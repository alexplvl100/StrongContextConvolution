**Объект исследования:** DeepSeek Harness (DSH) версии `@deepseek-ai/dsh@0.2.1-rc.2`

## 0. Главный вывод

**Гипотеза заказчика подтвердилась по направлению, но требует уточнения.**

Штатная компакция DSH сжимает историю **в 164–175 раз** и стоит **~1 % от
прогона** благодаря кэшу префикса. Ядро SCC сжимает в **3,6 раза** — то есть
**в 46–49 раз слабее**.

| | DSH-компакция | SCC |
|---|---|---|
| Коэффициент (замерено) | **×164–175** | ×3,6 |
| Стоимость прогона | **~1 %** (кэш 99 %) | ×3,1 дешевле сырого |
| Точные значения | **8 % путей** после 1 цикла | **100 %** (CAS + гейт) |
| Повторная обработка | пересказ пересказа | запрещена (маркер) |

**Уточнение, важное для решения.** Разница ×46 — это разница **между
«пересказать» и «сохранить точно»**, а не между «плохо» и «хорошо». Компакция
жертвует точными значениями; SCC их сохраняет. Вопрос не «что эффективнее», а
**что именно нужно в контексте**.

### Три находки, меняющие картину

**1. Поиск по истории выключен.** Пять штатных инструментов
(`session_search`, `session_event_search`, `session_trace`,
`session_event_trace`, `session_event_read`) существуют, но **не подключены**:
`openAt: never` в `dsh-base`. Проверено — их нет среди 31 инструмента в
`request/header`. **То есть модель не может дотянуться до архива вообще.**
Включение этого бандла открывает путь «контекст → архив по запросу» — это
архитектурная возможность, которой SCC пытается дать замену (Архивариус).

**2. Метаконтекст существует и не используется.** `AGENTS.md` с бюджетом
**65 536 байт** — штатный механизм `dsh-agent-instructions`, включён в
`dsh-base`. **Замерено: ни одного `AGENTS.md` в системе нет.** Это ровно та
«стационарная методологическая база», о которой говорит заказчик, — и она
доступна без разработки.

**3. Компакция теряет точные данные каскадом — ИЗМЕРЕНО.** Одна компакция
сохраняет **8 %** путей из исходника, вторая — оставляет **2,4 %** от исходных
840 путей. Каждый цикл теряет ~88 % оставшегося. SCC даёт **100 %** по гейту
маркера.

**4. Компакция почти бесплатна.** Из 543 436 токенов прогона **536 832 (98,8 %)
взято из кэша префикса**; оплачено **6 604 токена = 1,2 %**. Вторая компакция —
**0,8 %**. Механизм: пересказ дословно повторяет префикс разговора
(системный промт, инструменты, затенённые сообщения), поэтому провайдер
переиспользует кэш.

### Практический вывод по гипотезе

Увеличение `retainRatio` с 16 % до 50 % и создание `AGENTS.md` — **работают и
не требуют SCC ни строкой кода**:

| `retainRatio` | Дословно остаётся | Прирост до порога | Компакций на 10M токенов |
|---|---|---|---|
| 16 % (сейчас) | 158 689 | 626 768 | 16 |
| **50 % (предложено)** | **495 904** | 289 553 | 35 |
| 70 % | 694 265 | 91 192 | 110 |

Плата за 50 % — вдвое больше компакций, но каждая стоит **~1 % прогона**.

## 1. Какое окно контекста передаётся LLM

### 1.1. Состав запроса

Из `dsh-agent-loop/lib/index.js` (`buildRequest`):

```js
return markAgentLoopRequest(Object.freeze({
    ...header.config,                 // provider, model, maxTokens
    messages: boundaryMessages,       // session.deriveMessages()
    toolHistory: session.toolHistory(),
    ...header.tools !== void 0 ? { tools: header.tools } : {},
    sessionId: this.session.id,
    signal
}));
```

**Опровергнутое допущение: поля `system` в запросе НЕТ.**
`dsh-agent-loop/README.md:120`: «The request is `header.config`,
`deriveMessages()`, and `header.tools`; **it carries no `system` field**.»

Системный промт едет **первым элементом `messages`** с `role: system` — это
«surface node 0», официальный термин.

### 1.2. Замеренная структура (живая сессия)

| Часть | Объём | Доля | Сжимается компакцией |
|---|---|---|---|
| Системный промт (18 абзацев) | 5 622 симв (~1 405 ток) | 0,14 % | **НЕТ** |
| Схемы инструментов (31 шт) | 28 552 симв (~7 138 ток) | 0,71 % | **НЕТ** |
| История (видимая поверхность) | 663 986 симв (~166 000 ток) | 94 % | **ДА** |
| — `tool/result` (440 шт) | 577 057 симв | 87 % истории | да |
| — `assistant/message` (376) | 56 083 симв | 8 % | да |
| — `user/message` (37) | 25 224 симв | 4 % | да |
| runtime-context (1 снапшот) | ~1 349 симв | — | нет (заменяется) |
| time-context | ~251 симв | — | нет |

**Ключевое:** стационарная база — всего **8 543 токена (0,85 % окна)**. Основной
объём — история, и именно она сжимается.

### 1.3. Порог компакции

```
trigger = floor(min(W × thresholdRatio, W − O − headroomTokens))
```

При `W = 1 000 000`, `O = 8 192`, `B = 65 536`:

| Величина | Значение |
|---|---|
| `W × 0,8` | 800 000 |
| `W − O − B` | 926 272 |
| **Порог (работает первый)** | **800 000** = 80 % окна |
| Retention: 16 % от `W − O` | 158 689 ток |
| Сжимается за раз | 641 311 ток |

Секции промта (`SECTION_ORDERS`): `HARNESS_IDENTITY −1000`,

1100, write 1200, edit 1300, glob 1400, grep 1500, jobs 1600, web 2000/2100,

## 2. Хранилище сессии и штатные средства анализа

### 2.1. Физическое хранилище

```
~/.dsh/sessions/--<нормализованный-cwd>--/<закодированный-id>/session.v4.jsonl.zstd
```

**Одна строка = одно событие**, поверх — **независимые Zstandard-фреймы**:
первый фрейм содержит **только строку заголовка**, далее по фрейму на каждый
батч записи. Проверка жёсткая: «corrupt Zstandard session log: first frame is
not exactly one header line».

**Замерено на моей сессии:** 6 451 фрейм, header-фрейм 178 байт, медиана
фрейма ~1 034 байта, максимум 45 101. Распаковано **39,7 МБ / 13 007 строк**,
сжатие **×3,58**. Файл на диске 11,1 МБ.

Заголовок:

```json
{"type":"session","version":4,"id":"session-01d7fa7b-...",
 "createdAt":1792669302486,"cwd":"<проект>",
 "isSeeded":false,"delegationDepth":0,"agentPreset":"standard"}
```

**Append-only: ничего не удаляется.** «Nothing deletes session files — logs
accumulate under `root` until removed externally; the seam has no deletion API».

**Durability:** «Each subsequent batch appends lines or one compressed frame and
`fsync`s before the append resolves… Committed events are never rewritten».
Один живой писатель: in-process claim + kernel `flock(2)` на `session.lock`.

**Частичное чтение поддержано:** `stat`/`list` читают **только header-фрейм**;
`read(offset, length)` даёт логический срез по seq. Есть восстановление
«torn tail» — оборванный последний фрейм отдаёт только целые записи.

**Ничего не удаляется.** Компакция не стирает события, а **затеняет** их:
`surfaceOp: {op: "replace", startSeq, endSeq}`. Замерено в моей сессии:
3 909 surface-событий, из них **3 055 затенено, 854 видимо**.

### 2.3. Штатные средства анализа истории: есть, но ВЫКЛЮЧЕНЫ

**Да, есть — но по умолчанию отключены, и модель их не видит.**

Пакет `dsh-tool-session-query` даёт **пять read-only инструментов**:

| Инструмент | Что делает | Обязательные параметры |
|---|---|---|
| `session_search` | поиск по **прошлым сессиям**, лучшая находка на сессию | `query` |
| `session_event_search` | поиск по событиям **одной** сессии | `query` |
| `session_trace` | родословная сессии (предки/потомки) | `session_id` |
| `session_event_trace` | все замены и связи одного события | `session_id`, `seq` |
| `session_event_read` | полное чтение одного события + соседей | `session_id`, `seq` |

**Ключевое: по умолчанию они выключены.** `dsh-base/cordis.patch.yml`:

```yaml
- id: session-query-sqlite
  name: '@deepseek-ai/dsh-session-query-sqlite'
  config:
    path: ':memory:'
    openAt: never
```

Комментарий там же: «Full-text session search is opt-in. `openAt: never` keeps
`ctx.sessionQuery` mounted … while search calls fail with
`SESSION_QUERY_SEARCH_DISABLED` and SQLite is never opened».

Включается бандлом `dsh-experimental-session-search` (в Web и Desktop
**выключен по умолчанию**: «The bundle ships switched off in Web and Desktop»).

**Проверено эмпирически:** в `request/header` живой сессии **31 инструмент**, и
ни одного из пяти там нет:

```
session_search:       НЕТ
session_event_search: НЕТ
session_trace:        НЕТ
session_event_read:   НЕТ
```

**Вывод: модель не может искать по прошлой истории — механизм есть, но не
подключён.** Если его включить, откроется путь «контекст → архив по запросу»,
которого сейчас нет.

**Прочие средства анализа** (внутренние, модель их не видит):

| Средство | Что даёт |
|---|---|
| `dsh-session-query` + `-sqlite` | FTS5-индекс поверх журнала, schema 8 |
| `dsh-session-projection` | read-model: **27 ключей** (todo, goal, stats, outline) |
| `dsh-session-stats` | счётчики ходов и тайминги |
| `dsh-session-turn-outline` | навигация по ходам (превью 50/120 символов) |
| `dsh-session-log-export` | ZIP-экспорт журнала целиком |
| `dsh-experimental-session-inspector` | UI-инспектор (Raw Log / Chat Group) |
| `dsh-experimental-session-search` | бандл включения поиска |

**Проекции работают на этой машине:** `~/.dsh/storages/session_projcache/`
содержит запись для моей сессии, `version: 7`, **27 ключей проекций**.
Конфиг: `writeEveryEvents: 200`, `writeIntervalMs: 5000`.

**SQLite — отдельная производная база**, не индекс в хранилище: «Avoid pointing
`path` at the session-persistence database — this package owns a separate derived
index». Схема: `persisted_sessions` + `persisted_docs` (FTS5, `unicode61`) +
TEMP-двойники `live_*`.

## 3. Что попадает в контекст после компакции

### 3.1. Состав замены

Компакция **заменяет** диапазон истории одним сообщением. Что в нём:

```markdown
This is an automatically generated checkpoint condensing an earlier span of the
conversation to free up context. Treat the captured context as established
background and build on it without restating it. Continue the task directly from
the messages that follow, without acknowledging this checkpoint.

<compacted-summary>
...структурированный пересказ...
</compacted-summary>
```

Маркеры: `SUMMARY_OPEN_TAG = "<compacted-summary>"`,
`SUMMARY_CLOSE_TAG = "</compacted-summary>"`.
Плюс служебный маркер `COMPACT_CHECKPOINT_MARKER = {kind: "compact-checkpoint"}`
для распознавания в персистентности.

### 3.2. Структура пересказа (жёстко задана)

Инструкция компакции требует **ровно восемь разделов**:

```
## Primary Request and Intent
## Key Technical Concepts
## Files and Code
## Errors and Fixes
## Pending Jobs
## Current Work
## Next Step
## Critical Context
```

С правилами: «Use terse bullets, not prose paragraphs. Write "(none)" for an
empty section — never drop a section.» И: «Preserve exact file paths, commands,
error strings, identifiers, numeric values, function signatures».

**Это ровно та структура, которую я получил в своём чекпойнте в начале сессии.**

### 3.3. Что ЕЩЁ попадает в контекст (ответ на вопрос «подсовывается ли что-то»)

**Да, и это существенно.** Кроме пересказа, в контекст входят **четыре
источника, не сжимаемые компакцией**:

1. **Системный промт** — пересобирается **на каждом шаге** (`agent/pre-step`).
   Компакция его не трогает: README прямо говорит «cannot reduce the system
   prompt, tools, or session prefix».
2. **Схемы инструментов** — отдельное wire-поле `tools`, **27,5 КБ / ~7 138
   токенов**, оплачивается **на каждом шаге**.
3. **Runtime-context** — `user/message` со `source.kind='runtime-context'`,
   **заменяется только при изменении**. Содержит: рабочий каталог, политику
   песочницы, политику подтверждений, расположение чекаута DSH, URL GUI.
4. **Time-context** — `user/message` со `source.kind='time-context'`, интервал
   по умолчанию **10 минут**: метка времени, часовая зона браузера, прошедшее
   время.

### 3.4. Замеренная видимая поверхность после двух компакций

| Тип | Видимых | Символов |
|---|---|---|
| `tool/result` | 440 | 577 057 |
| `assistant/message` | 376 | 56 083 |
| `user/message` | 37 | 25 224 |
| `system/message` | 1 | 5 622 |
| **Итого** | **854** | **663 986** |

При 3 909 surface-событиях всего: **затенено 3 055 (78 %), видимо 854 (22 %)**.

## 4. Что заставляет модель обращаться к дополнительным источникам

Это ключевой вопрос заказчика. Механизмов **шесть**, и все работают **без
команды пользователя**.

### 4.1. Системный промт: 18 абзацев инструкций

Самый сильный источник. Замерено: **5 622 символа, ровно 18 абзацев**. Владельцы
установлены: `dsh-system-prompt` (идентичность, 48 симв), `dsh-persona`
(персона, 73), `dsh-file-reference` (407), `dsh-tool-bash` (92), `dsh-tool-fs`
(read 126, write 140, edit 132), `dsh-tool-fs-search` (glob 71, grep 129),
`dsh-tool-jobs` (382), `dsh-tool-web` (215+150), `dsh-tool-goal` (528),
`dsh-tool-workflow` (325), `dsh-tool-subagent` (139), `deliverables` (1304),
`dsh-harness-dev-context` (325+1002).

**Каждая секция — прямое указание, какой инструмент и когда применять.**

### 4.2. Схемы инструментов: сами описания

**27 557 байт** описаний с сигнатурами. `dsh-tools/README.md`: «the model sees
each visible definition's exact name, description, and JSON Schema». Это
**не пассивный справочник** — это приглашение к вызову.

### 4.3. Runtime-context: рабочий каталог и политики

Обновляется при изменении. Сообщает модели, **где она находится** и **что ей
можно**. Без этого она не знает, куда применять инструменты.

### 4.4. Time-context: часы

Каждые 10 минут. «It helps the model interpret otherwise-unqualified dates and
times in the user's browser zone». Плюс: «tells it to ask when current-turn
browser zones are mixed or missing».

### 4.5. `developer/message`: изменения набора инструментов

`dsh-agent-loop/README.md:156`: «Comparing their names with the preceding header
emits one `developer/message` for additions and removals, **independently of
model capability**». То есть при появлении/исчезновении инструмента модель
**явно уведомляется** — и это происходит без участия пользователя.

### 4.6. AGENTS.md / CLAUDE.md — **метаконтекст проекта** (не задействован!)

Самый прямой ответ на гипотезу заказчика. `dsh-agent-instructions`:

> «The first request includes one durable baseline message with the user-global
> chain — `$DSH_HOME/AGENTS.md`, then `<agentsHome>/AGENTS.md` — followed by the
> project chain: every existing candidate file from the project root down to the
> session working directory, in broad-to-specific order.»

Бюджет: **`maxBytes: 65536`**. Обёртка: `<system-reminder>`.
Кандидаты: `AGENTS.md`, `CLAUDE.md`, `AGENTS.local.md`, `CLAUDE.local.md`.

**Плагин АКТИВЕН — доказано документально:**

```yaml
# dsh-base/cordis.patch.yml:303-306
- id: agent-instructions
  name: '@deepseek-ai/dsh-agent-instructions'
  config:
    maxBytes: 65536
```

```yaml
# dsh-web-app/presets/standard.patch.yml:15-18
- id: agent-instructions
  name: '@deepseek-ai/dsh-agent-instructions'
  config:
    maxBytes: 65536
```

Стандартный пресет — тот, на котором работает эта сессия — **содержит плагин**.
То есть механизм не просто существует, он **загружен и ждёт файлов**.

**Замерено: файлов НЕТ ни одного.**
Проверено: `~/.dsh/AGENTS.md`, `~/.agents/AGENTS.md`,
`<проект>/AGENTS.md` — **ни одного файла**.

**Проверено по журналу сессии:** вставки не произошло.

| Проверка | Результат |
|---|---|
| `source.kind='instructions'` в user/message | **0 вставок** (только упоминания в моих ответах) |
| Первые 8 `user/message` | `user`, `runtime-context`, `time-context` — метаконтекста нет |
| `system-reminder` (обёртка плагина) | 18 вхождений, но **все в моих же текстах**, не вставка |

**Вывод: штатный механизм стационарного метаконтекста существует, загружен в
стандартный пресет, но не используется — файлов нет.** Создание `AGENTS.md`
**включает его без единой строки кода**.

|---|---|---|
| `dsh-repeat-tool-reminder` | 3, 5, 8 повторов вызова с теми же аргументами | просит сменить подход |
| Восстановительные `tool/result` | прерывание шага | `ABORTED_BEFORE_DISPATCH`, `TOOL_OUTCOME_UNKNOWN`, `TOOL_NOT_STARTED` |

## 5. Алгоритм восстановления контекста после компакции

### 5.1. Восстановление НЕ требуется — контекст выводится из журнала

Ключевое понимание: **сжатый контекст не хранится отдельно**. При каждом
запросе он **выводится заново** из append-only журнала:

```
журнал (11 682 события, ничего не удалено)
    │
    ├── compaction/summary: "затени эти seq"
    │
    ▼
deriveMessages(): применяет surfaceOp
    │
    ├── затенённые события -> НЕ попадают в messages
    └── видимые -> попадают в messages
    │
    ▼
messages для LLM (854 видимых события)
```

`dsh-session/README.md:127`: «`deriveMessages()` caches deep-frozen projections
and returns a fresh array per call... Replacements and projection decisions
invalidate the cache.»

### 5.2. Транзакция компакции (точно)

```
1. compaction/start                 <- блокировка, log-only
2. подготовка и вызов пересказа     <- LLM, ctx.llm.stream()
3. повторная проверка стабильности
4. проверка «пересказ меньше источника» (иначе отказ)
5. compaction/summary               <- запись пересказа, log-only
6. user/message с surfaceOp=replace <- ЕДИНСТВЕННАЯ мутация поверхности
7. compaction/end                   <- снятие блокировки
```

«A live unmatched start is the durable lock»: незакрытый `compaction/start` —
это признак занятости. При сбое закрытия остаётся «orphan», намеренно
блокирующий.

### 5.3. Восстановление после сбоя — `session-checkpoint-policy`

«Work can resume after a crash from stored requests, tool calls, responses, and
results without loss. Checkpoint failures are fail-closed: a model adapter or
top-level tool body does not run until the durable write succeeds.»

### 5.4. Восстановление после переполнения окна

`agent/request-error` ловит `CONTEXT_WINDOW_EXCEEDED`: «bypasses the normal
threshold and retention policy, attempts one maximal balanced head reduction,
and authorizes a retry only after the surface replacement generation advances».

### 5.5. Что НЕ восстанавливается

- Затенённые события **доступны только через `session_search`** или чтение
  журнала напрямую. В контекст они не вернутся. **Но `session_search` выключен**,
  поэтому модель до архива дотянуться не может вовсе.
- **Перехода «архив → контекст» нет.** Аналог инварианта 2 SCC.

### 5.6. Полный список типов событий: 63

`KNOWN_SESSION_EVENT_TYPES` содержит **ровно 63 типа**; событие вне множества
отвергается, если не помечено `ignorable: true`. **Surface-типов только 5**
(`system/message`, `developer/message`, `user/message`, `assistant/message`,
`tool/result`) — лишь они дают сообщения модели.

**В моей сессии встретилось 33 типа.** Топ: `tool/result` 1 912, `tool/call`
1 901, `step/start` 1 784, `assistant/message` 1 783, `step/end` 1 783,
`job/registered` 1 561, `job/settled` 1 561, `agent/inbox/spliced` 210,
`user/message` 166, `turn/start` 68. Компакция: `compaction/prune` 11,
`compaction/start|summary|end` по 2.

**Правило: модель-видимое = залогированное.** Всё, что попало в контекст,
записано в журнал; всё, что не записано, в контекст не попадало.

## 6. Проверка гипотезы заказчика

### 6.1. Гипотеза

> «Вся затея SCC и трёхуровневой памяти неэффективна, и увеличение размеров
> пересказанного контекста с 16 % до 50 % + стационарная методологическая база
> (метаконтекст проекта) решат все проблемы.»

### 6.2. Что подтвердилось

**1. SCC сжимает в 46–49 раз слабее.** Замерено на моей же сессии:

| | Сжато | Пересказ | Коэффициент |
|---|---|---|---|
| Компакция #1 | 631 500 ток | 3 611 ток | **×175** |
| Компакция #2 | 631 629 ток | 3 854 ток | **×164** |
| SCC (ядро) | — | — | ×3,6 |

**2. Компакция почти бесплатна.** Кэш префикса: из 543 436 токенов прогона
**536 832 (98,8 %) из кэша**. Оплачено **6 604 токена = 1,2 %**. Вторая
компакция: 99,2 % из кэша, оплачено **0,8 %**.

Механизм: «Replaying the system prompt held by the `system/message` at surface
node 0, the last routed request's tools, and the shadowed-region messages
**byte-for-byte** makes the auxiliary call a genuine prefix of the conversation».

**3. Увеличение `retainRatio` работает.** 50 % даёт 495 904 токена дословно
вместо 158 689 — втрое больше. Плата: вдвое больше компакций (35 против 16 на
10M токенов), но каждая ~1 % прогона.

**4. Метаконтекст существует и не используется.** `AGENTS.md` с бюджетом
65 536 байт — штатный механизм, включён в `dsh-base`, но файлов нет.

### 6.3. Что НЕ подтвердилось

**1. «Неэффективность» SCC — вопрос назначения, а не эффективности.**
Компакция **теряет точные значения**: это её задокументированное свойство
(«retains only its summary text»). SCC сохраняет их через CAS. Разница ×46 —
это **цена сохранности**, а не потери.

**2. Пересказ пересказа — не случайность, а замысел.** Инструкция компакции
**явно предусматривает** повторную консолидацию:

> «If the conversation already contains a `<compacted-summary>` block, it is a
> PRIOR checkpoint. Do not copy it forward verbatim: preserve still-true facts,
> drop stale ones, and merge newer information into a single consolidated
> summary under the same structure.»

**Замерено: пересказ #1 (seq 5979) вошёл во вход пересказа #2** (диапазон
`5979..10213`). Это **сознательная консолидация**, и она объясняет, почему
структура из восьми разделов обязательна: она позволяет мержить.

**3. Потеря фактов при пересказе — ИЗМЕРЕНО.** Пересказ теряет точные
значения, но **неравномерно**: пути сохраняются в 4,7 раза лучше среднего
текста. Инструкция «Preserve exact file paths, commands, error strings,
identifiers, numeric values» **работает**. Подробно — §6.4.

### 6.4. Выживаемость фактов при пересказе (замер)

Метод: сравнил **исходный текст затенённых событий** с текстом пересказа.
Считались уникальные пути (`/...`) и числа от 3 цифр.

**Одна компакция:**

| Компакция | Исходник | Пересказ | Текст | Пути | Числа |
|---|---|---|---|---|---|
| #1 | 845 843 симв | 14 445 симв | **1,7 %** | **8,0 %** | 5,6 % |
| #2 | 619 718 симв | 15 417 симв | **2,5 %** | **11,6 %** | 6,6 % |

**Обогащение по путям: ×4,7 в обеих компакциях.** Прямое подтверждение, что
инструкция сохранять точные пути **исполняется моделью**.

**Каскад «пересказ пересказа»** (пересказ #1 → пересказ #2):

| Что | В #1 | Выжило в #2 | Потеряно |
|---|---|---|---|
| Пути | 49 | **6 (12,2 %)** | 43 (87,8 %) |
| Числа | 60 | **7 (11,7 %)** | 53 (88,3 %) |

**Полная воронка** (пути от исходника до второго пересказа):

```
840 путей в исходнике
  → 67 (8,0 %)  после компакции #1
  → 20 (2,4 %)  после компакции #2
```

**Что это значит.** Каждый цикл пересказа теряет **~88 %** путей, оставшихся
от предыдущего. Каскад из десяти компакций не оставит от исходных точных
данных практически ничего.

**Это и есть замеренное подтверждение тезиса SCC.** Штатная компакция **не
гарантирует** сохранность точных значений, и её инструкция этого не обещает:
она просит сохранять пути «where the exact wording matters», то есть **по
суждению модели**, а не все.

**Сопоставление с SCC:** SCC даёт **полное покрытие** по гейту маркера
(проверено ранее: 140/140 имён файлов, 891/892 события). Компакция даёт **8 %**
путей после первого пересказа и **2,4 %** после второго.

### 6.5. Итоговая проверка гипотезы

**Направление верное, но формулировка требует уточнения.**

| Утверждение | Оценка | Число |
|---|---|---|
| SCC слабее по коэффициенту | **верно** | ×3,6 против ×164–175 (×46) |
| Компакция дорогая | **неверно** | ~1 % прогона (кэш 99 %) |
| `retainRatio` 50 % лучше 16 % | **верно** | 158 689 → 495 904 ток |
| Метаконтекст решит проблемы | **вероятно** | механизм есть, 64 КБ, не используется |
| Компакция сохраняет точные данные | **неверно** | 8 % путей после #1, 2,4 % после #2 |
| «Решат ВСЕ проблемы» | **не подтверждено** | точные данные теряются каскадом |

**Ключевое уточнение:** компакция и SCC решают **разные задачи**.

- **Компакция** — удержать **смысл** истории при минимальном объёме, ценой
  точных значений. Для «что было» этого достаточно.
- **SCC** — сохранить **точные значения** (пути, хеши, числа). Для «какой
  именно путь был» пересказ не годится: после двух циклов остаётся 2,4 %.

**Замеренная цена размена:**

| | Компакция | SCC |
|---|---|---|
| Объём после сжатия | ×164–175 меньше | ×3,6 меньше |
| Сохранность путей | **2,4 %** после 2 циклов | **100 %** (гейт маркера) |
| Стоимость | ~1 % прогона | ×3,1 дешевле сырого |

Если точные значения не нужны — **штатная компакция выигрывает по объёму**.
Если нужны — SCC дополняет её, но **не заменяет**, и его ×46 по объёму есть
цена 100 % сохранности.

## 7. Что это значит для проекта SCC

### 7.1. Практические ходы без разработки

| Действие | Эффект | Цена |
|---|---|---|
| `retainRatio: 0.16 → 0.50` | втрое больше дословного (158 689 → 495 904) | вдвое больше компакций |
| Создать `AGENTS.md` | стационарный метаконтекст, **не сжимается** | 1,64 % окна на полный бюджет |
| `headroomTokens` уменьшить | компакция раньше, больше запас | чаще вызовы |
| `modelPolicies` | свои пороги под модель | — |

Все четыре — **конфигурация**, без кода.

**Замер бюджета метаконтекста** (бюджет 65 536 байт ≈ 16 384 ток):

| | Токенов | Доля окна 1M |
|---|---|---|
| Промт сейчас | 1 405 | 0,14 % |
| Схемы инструментов | 7 138 | 0,71 % |
| **База всего** | **8 543** | **0,85 %** |
| + `AGENTS.md` на полный бюджет | 24 927 | **2,49 %** |

**Влияние на частоту компакций** (при `retainRatio 50 %`):

| | Цикл роста | Компакций на 10M токенов |
|---|---|---|
| Без метаконтекста | 275 169 | 36 |
| С метаконтекстом | 258 785 | 38 |

**Полный бюджет метаконтекста стоит 1,64 % окна и добавляет 2 компакции на
10M токенов.** Это дешёвая плата за стационарную базу знаний, которая
**никогда не сжимается и не теряется**.

### 7.2. Что SCC даёт поверх компакции

1. **Точные значения через CAS.** Пересказ их теряет; ссылка `CAS?{хеш}?`
   сохраняет побайтово.
2. **Маркер неприкосновенности `(_SSC_)`.** Запрещает повторную свёртку.
   Компакция же **пересказывает пересказ** — правда, сознательно.
3. **Гейт полноты.** SCC проверяет, что все события покрыты; компакция просто
   доверяет модели.

### 7.3. Где SCC проигрывает и что с этим делать

**Коэффициент ×3,6 против ×164.** Причина: SCC хранит точные данные, компакция
их выбрасывает. Это осознанный размен, но его **надо назвать числом** — что
именно стоит ×46 по контексту.

**Возможное направление:** использовать **штатную компакцию как средний
уровень**, а SCC — только для данных, требующих точности. Это архитектурный
вопрос, требующий отдельного решения заказчика.

## 8. Штатные настройки компакции (справочник)

| Поле | По умолчанию | Смысл |
|---|---|---|
| `thresholdRatio` | `0.8` | доля окна в `floor(min(W × r, W − O − B))` |
| `headroomTokens` | `65536` | запас поверх резерва вывода |
| `retainRatio` | `0.16` | доля `W − O`, хранимая дословно |
| `retainTokens` | — | абсолютный бюджет (взаимоисключим с `retainRatio`) |
| `summarizationProvider` / `Model` | `''` | кем пересказывать |
| `maxTokens` | `= headroomTokens` | предел вывода пересказа |
| `compactionRetries` | `1` | повторы при остаточном давлении |
| `maxOverflowRetries` | `1` | повторы после переполнения окна |
| `modelPolicies` | `[]` | точные переопределения `{provider, model, ...}` |
| `auto` | `true` | автокомпакция и восстановление |

**Прунер** (`dsh-compaction-tool-result-pruner`): `headChars: 4096`,
`tailChars: 1024`. Работает **без LLM**, может отменить пересказ вовсе.

**Ограничения** (задокументированы): не сжимает системный промт, инструменты и
префикс сессии; не делит неделимый узел; точность метр-эвристики —
**4 символа = 1 токен** (тот же коэффициент, что в SCC).

1. **Одна сессия.** Замеры компакции — на `session-01d7fa7b` (11 682 события,
