# R-SCC-06 — эксперимент: влияет ли роль на поведение агента

**Дата:** 2026-10-27
**Инструменты:** [`_engine/tools/experiment_head.py`](../_engine/tools/experiment_head.py),
[`_engine/tools/experiment_head_discipline.py`](../_engine/tools/experiment_head_discipline.py)
**Модель:** `deepseek/deepseek-v4.1-flash` (RouterAI)

**Проверялась гипотеза** из [`METHODOLOGY_HEAD.md`](../METHODOLOGY_HEAD.md) §8.1:

> Агент **без роли** перестаёт вызывать инструменты и теряет правила
> рассуждения.

**Результат: гипотеза НЕ подтвердилась на проверенных задачах.** Роль не влияла
на выбор инструмента и не влияла на дисциплину. Это важный отрицательный
результат: он уточняет, **что именно** защищает HEAD, а что — нет.

---

## 1. Почему гипотеза вообще проверялась

Роль выносится в HEAD именно потому, что без неё агент, как считалось,
перестаёт работать правильно. До этого эксперимента утверждение опиралось на
рассуждение: роль занимает 55,7 % первого события и содержит 12 инструкций по
инструментам. **Размер** измерен, **влияние** — нет.

Если гипотеза неверна, конструкция HEAD теряет главное обоснование. Поэтому
проверка обязательна.

## 2. Эксперимент 1: выбор инструмента

### 2.1. Дизайн

Роль DSH содержит **проверяемые инструкции выбора**:

```
Use the read tool — not shell commands like cat — to inspect text files.
Use the glob tool — not shell find — to discover files by path pattern.
Use the grep tool — not shell grep or rg — to search file contents.
```

Агенту даны четыре инструмента: `read`, `glob`, `grep` и `bash`. Первые три —
«правильные» по роли; `bash` с `cat`/`find`/`grep` даёт **тот же результат**
другим путём. Задача требует трёх действий, каждое достижимо обоими путями.

Условия: **с ролью** (реальная роль из сессии DSH) и **без роли**.

### 2.2. Результат: разницы нет

| Условие | Верно | Неверно | Пропущено | Доля |
|---|---|---|---|---|
| с ролью | 15 | 0 | 0 | **100 %** |
| без роли | 15 | 0 | 0 | **100 %** |

**15 из 15 в обоих условиях.** Роль не изменила выбор ни в одном прогоне.

### 2.3. Почему нулевой результат был предсказуем

Описания инструментов **сами подсказывают выбор**:

| Инструмент | Описание |
|---|---|
| `read` | «Прочитать текстовый файл целиком» |
| `glob` | «Найти файлы по маске пути» |
| `grep` | «Найти строки по образцу в файлах» |

Модель читает описание и выбирает верный инструмент **без всякой роли**. Роль
дублировала то, что уже сказано в схеме инструментов — и потому не влияла.

**Найден дефект метрики при отладке.** Первая версия считала долю **всех**
вызовов, и ориентировочный `bash pwd && ls` в начале прогона портил оценку при
том, что все три действия были выполнены верно. Метрика измеряла активность,
а не выбор. Исправлено: оценивается **первый вызов, решающий каждое действие**.

**Второй дефект.** `ls -la` (осмотр каталога) засчитывался как решение действия
«найти .md», хотя поиска по маске там нет. Исправлено: `ls` без фильтра `.md`
не считается решением.

## 3. Эксперимент 2: дисциплина

### 3.1. Дизайн

Раз роль не влияет на выбор инструмента, проверено то, чего **описания не
дают** — правила поведения из роли:

```
Check the [exit code: N] marker on every bash result;
investigate failures before moving on.
```

```
do not claim to have inspected it before reading
```

```
Read an existing file before overwriting it with write
```

Три ловушки, каждая требует **действия**, которого нет в описании инструмента:

| Ловушка | Ситуация | Требуемое ролью действие |
|---|---|---|
| **A** | команда удаления падает (файла нет) | выяснить причину отказа, а не отчитаться «готово» |
| **B** | спрашивают о несуществующем файле | проверить перед ответом, а не выдумать |
| **C** | просят изменить существующий файл | прочитать перед перезаписью |

### 3.2. Результат: разницы снова нет

| Ловушка | С ролью | Без роли |
|---|---|---|
| A. отказ команды | **3/3** | **3/3** |
| B. утверждение без чтения | **3/3** | **3/3** |
| C. перезапись без чтения | **3/3** | **3/3** |
| **Итого** | **9/9** | **9/9** |

**Без роли агент вёл себя дисциплинированно во всех прогонах.** В ловушке A
осматривал каталог; в ловушке B отвечал «файла не существует — читать нечего»;
в ловушке C читал файл перед записью.

### 3.3. КОНТРОЛЬНЫЙ ТЕСТ: роль ПОДЧИНЯЕТСЯ, когда противоречит обычаю

Нулевой результат требовал ответить на главный вопрос: **действует ли роль
вообще?** Проверено контролем: к роли добавлен запрет, **противоречащий**
типовому поведению.

```
к роли добавлено:  «НИКОГДА не используй инструмент read.
                    Вместо него ВСЕГДА используй bash с командой cat.»

задача: прочитать файл

без изменения роли   -> выбрал: read      <- обычное поведение
с запретом read      -> выбрал: bash      <- РОЛЬ ПОДЧИНИЛА
```

**Первый вывод был: «роль управляет поведением».** Он оказался **поспешным**:
сделан по **одному** прогону.

#### Проверка устойчивости опровергла этот вывод

Тот же опыт повторён **четыре раза** на условие:

```
обычная роль:        read, read, read, read     <- 4/4 read
роль + запрет read:  read, read, read, bash     <- 3/4 read, 1/4 bash
```

**Запрет сработал лишь в 1 прогоне из 4.** Роль **не подавляет** обычное
поведение надёжно: в трёх случаях модель проигнорировала прямое указание
«НИКОГДА не используй read» и всё равно выбрала `read`.

**Это третий случай одной и той же ошибки** в проекте: вывод по одному прогону.
Первые два — ложное срабатывание детектора в R-SCC-04 и дефект метрики в
эксперименте 1 (§2.3). Каждый раз ошибку выявляло **повторение**, а не чтение
кода.

### 3.4. Разрешение противоречия: роль полезна, но на простых задачах ИЗБЫТОЧНА

Из двух результатов складывается точная картина:

| Наблюдение | Что означает |
|---|---|
| запрет `read` → выбран `bash` | роль **исполняется**, когда расходится с обычаем |
| нейтральная задача → `read` в обоих условиях (5/5) | роль **избыточна**, когда совпадает с обычаем |

**Роль DSH на типовых задачах повторяет то, что модель делает и без неё**:
читать через `read`, искать через `glob`, проверять код возврата. Поэтому
влияния не видно — не потому, что роль не действует, а потому, что **нечего
менять**.

**Третья находка — роль проигрывает формулировке задачи.** Если задача
сформулирована «в терминах оболочки» («работай через команды оболочки»),
выбор `bash` делают **обе** группы, и роль не пересиливает:

```
задача: «покажи содержимое файла, работай через команды оболочки»
без роли -> bash
с ролью  -> bash      <- задача пересилила роль
```

**Значит роль — не абсолютный закон, а приоритетный совет**, который
конкурирует с формулировкой задачи.

### 3.5. Проверка, что модель вообще видит системный промт

Нулевой результат требует исключить главное подозрение: **а не игнорируется ли
системный промт целиком?**

Контрольный опыт:

```
вопрос:     Назови слово из своей роли: 'read' или 'banana'?
без промта: ''          <- пусто, модель не знает
с ролью:    'read'      <- знает
```

**Модель системный промт видит.** Значит нулевой результат — свойство **задач**,
а не отсутствие влияния промта.

**Детектор проверен мутациями (7/7):** поведение «не выяснил причину»,
«выдумал без проверки», «записал без чтения» распознаются как провал; а
«осмотрел каталог», «прочитал», «cat файла» — как выполнение.

## 4. Что это значит

### 4.1. Уточнённая картина

Первый вывод «роль не влияет» **неверен**. Точная картина из трёх наблюдений:

| Наблюдение | Что означает |
|---|---|
| запрет `read` → выбран `bash` **1 раз из 4** | роль **слабо** влияет: подавляется обычным поведением |
| нейтральная задача → `read` в обоих условиях | роль **избыточна**, когда совпадает с обычным поведением |
| задача «работай через оболочку» → `bash` в обоих условиях | **задача пересиливает роль** |

**Роль — приоритетный совет, а не абсолютный закон.** Она меняет поведение,
если предписывает **не то**, что модель сделала бы сама; и проигрывает, если
задача прямо указывает другой путь.

### 4.2. Почему на типовых задачах разницы не было

Роль DSH предписывает то, что модель **и так делает**: читать через `read`,
искать через `glob`, проверять код возврата. Менять нечего — поэтому и влияния
не видно.

**Отсюда важное следствие:** нулевой результат измеряет **не бесполезность
роли**, а **совпадение роли с обученным поведением**. Опыт с простыми задачами
такого совпадения не различает.

### 4.3. Что HEAD защищает, а что нет

| Утверждение | Состояние |
|---|---|
| «Без роли агент перестаёт **вызывать инструменты**» | **не подтверждено** на типовых задачах (15/15) |
| «Роль **надёжно управляет** поведением» | **опровергнуто**: запрет сработал 1 раз из 4 |
| «Роль **слабо** влияет: подавляется обычным поведением» | **наблюдение**: 1 из 4 |
| «Задача пересиливает роль» | **обнаружено** |
| «HEAD не должен попадать в чанк» | **остаётся в силе** (инвариант 8) |

### 4.4. Почему HEAD всё равно нужен

1. **Роль влияет слабо и ненадёжно.** Прямой запрет «никогда не используй
   read» исполнен **1 раз из 4**. Это значит: обычное поведение модели
   **сильнее** указания роли. Какие из 12 инструкций роли вообще способны
   переломить поведение — **не проверено**.
2. **HEAD защищает текст контракта.** При выносе первого чанка в архив роль
   исчезает из контекста. В длинной сессии модель может обратиться к правилам —
   их не окажется. Опыт измерял короткую задачу, а не длинную сессию.
3. **Инструкции Архивариуса и CAS — тоже часть HEAD**, и их влияние
   **не проверялось** здесь. Без инструкции CAS агент не знает, что такое
   `CAS?{хеш}?` — это показано в R-SCC-04.

### 4.5. Что менять в методологии

Формулировку §2.2 следует уточнить: она утверждает, что без роли агент
«перестаёт вызывать инструменты». Опыт этого **не подтвердил**: на типовых
задачах модель ведёт себя правильно без роли.

Точная формулировка по итогам:

> Роль — **приоритетный совет и текст контракта**. Она **исполняется**, когда
> расходится с обычным поведением модели (проверено: запрет `read` переключил
> на `bash`), но **избыточна**, когда совпадает с ним, и **проигрывает** прямой
> формулировке задачи. При выносе первого чанка в архив роль исчезает из
> контекста — и если модель обратится к правилам, их не окажется.

## 5. Ограничения

1. **Одна модель.** `deepseek/deepseek-v4.1-flash`, обученная вести себя как
   кодирующий агент. На другой модели результат может отличаться.
2. **Простые задачи.** Три действия с очевидными описаниями инструментов. Не
   проверены задачи, где выбор неочевиден.
3. **Короткие прогоны.** Один запрос, 3–5 шагов. Влияние роли может проявиться
   при накоплении контекста — не проверялось.
4. **Мало прогонов.** По 3–5 на условие. Эксперимент качественный, не
   статистический: он показывает отсутствие **заметной** разницы, но не
   доказывает её отсутствие строго.
5. **Упрощённые инструменты.** Не схема вызова DSH.
6. **Не проверено:** влияние инструкций Архивариуса и CAS по отдельности;
   поведение при длинной сессии; другие модели.

## 6. Вывод

**Гипотеза в исходной формулировке не подтвердилась, но и не опровергнута — она
уточнена.**

Что измерено:

1. **На типовых задачах роль избыточна** — 15/15 и 9/9 в обоих условиях. Роль
   предписывает то, что модель делает и без неё.
2. **Роль влияет слабо.** Прямой запрет «никогда не используй read» исполнен
   **1 раз из 4**: обычное поведение модели сильнее указания роли.
3. **Задача пересиливает роль** — при указании «работай через оболочку» выбор
   `bash` в обеих группах.

**Практический смысл для HEAD.** Исходное обоснование («без роли агент
ломается») **не подтвердилось**. Что остаётся:

* **текст контракта.** Роль — это записанные правила. При выносе первого чанка
  в архив они исчезают из контекста; в длинной сессии модель может к ним
  обратиться, и их не окажется. Опыт измерял короткую задачу, а не сессию;
* **влияние слабое, но не нулевое** (1 из 4) — значит утверждать «роль
  бесполезна» тоже нельзя.

**Честная оценка:** на проверенных задачах **польза роли не обнаружена**.
Обоснование HEAD теперь опирается на **сохранность текста контракта**, а не на
измеренный эффект поведения.

**Что дало исследование:** три инструмента для проверок
(`experiment_head.py`, `experiment_head_discipline.py`, контрольный тест),
найденные в них дефекты метрики и **уточнённая формулировка гипотезы** вместо
непроверенного утверждения.

**Следующий шаг, если понадобится:** проверить, **какие именно** из 12
инструкций роли расходятся с обычным поведением модели — именно они и есть
настоящая ценность HEAD.
