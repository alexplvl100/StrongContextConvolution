# R-SCC-02 — прогон SCC на собственном контексте агента

**Дата:** 2026-10-24
**Модель:** `deepseek/deepseek-v4.1-flash` (RouterAI)
**Данные:** журнал собственной сессии агента `session-01d7fa7b` —
**3 059 записей, 2 767 КБ (сжат), 892 события, 0 компакций**
**Статус:** прогон завершён, найдено **четыре дефекта, все исправлены**

Это первый прогон SCC на **живом рабочем контексте**, а не на тестовом корпусе.
T2 был синтетикой (sha256-цепочки); здесь — реальная сессия агента, который
разбирал устройство DSH, писал инструменты и общался с человеком.

файлов. Он подтвердил идею, но **не мог выявить дефекты масштаба** — слишком

|---|---|---|
| событий | 159 | **892** |

| типы событий | чтения файлов | bash, edit, subagent, ask_user, todo, goal |
| протокол | один | смешанный (русский диалог + код) |

## 3. ДЕФЕКТ 1: модель сменила формат заголовков на Markdown

**Симптом.** Гейт `scc_chunk.py check` вернул код 2 («НЕ ИЗМЕРЕНО: событий
E<N> не найдено») на файле, где было **891 событие**.

**Причина.** На большом контексте модель перешла на Markdown-разметку:

```
**E0: SYSTEM (seq 7)** — шапка роли: агент-кодер на `deepseek/...`
**E1: USER (seq 8)** — «проект не трогай, найди в DSH настройки...»
```

Парсер ожидал строго `E0: ...` без обёртки. Итог: **0 событий из 891**, и это
означало бы молчаливую потерю всего ядра при чанковании.

**Почему не выявил T2.** Там вывод был маленьким (5 797 символов), модель
держала простой формат. Формат «поехал» только при 892 событиях.

**Класс ошибки — самый опасный в схеме:** не исключение, не падение, а
**тихий ноль**. Гейт честно сказал «не найдено», но при автоматическом прогоне
это выглядело бы как «событий нет» и чанк-1 оказался бы пустым.

**Исправлено.** Регулярка допускает необязательную обёртку `**`:

```python
EVENT_RE = re.compile(
    r"^(?P<bold>\*\*)?"
    r"(?P<label>E\d+(?:\s*[–\-]\s*E\d+)?)"
    r"\s*:\s*"
    r"(?P<mark>\(_SSC_\))?",
    re.MULTILINE,
)
```

Добавлено 7 тестов на Markdown-заголовки, включая диапазоны и сшивку.

## 4. ДЕФЕКТ 2: гейт давал ложное нарушение на цитате

**Симптом.** После исправления формата гейт вернул код 1: «маркер продублирован
в 1 событиях».

**Причина.** Событие `E681` описывало постановку задачи, **цитируя маркер**:

```
E681: (_SSC_) USER (seq 2408) — большое задание: SCC, три этапа,
      постфикс `(_SSC_)`, алгоритм чанкования, методология, пуш в ...
```

Наивная проверка «сколько раз `(_SSC_)` встречается в первой строке» дала 2 и
объявила нарушение. Но второй маркер — **часть текста**, а не разметка.

**Почему это важно.** Мысль о маркере будет цитироваться в задачах, README и
обсуждениях — то есть ложное срабатывание возникало бы **каждый раз**, когда
контекст содержит слово `(_SSC_)`. Гейт, который срабатывает на собственное
описание, бесполезен.

**Исправлено.** Признак двойной простановки — маркер, идущий **сразу за
маркером** (`E0: (_SSC_) (_SSC_) SYSTEM`), а не упоминание в описании.
Добавлено 3 теста: цитата в теле (чисто), два маркера подряд (нарушение),
маркер после метки один раз (чисто).

## 5. ДЕФЕКТ 3: потолок вывода 131 072 токена режет этапы

**Симптом.** Этапы II и III дали **ровно** `completion_tokens: 131072` — это
2¹⁷, круглое число. Признак обрыва по лимиту, а не завершения.

**Последствия измерены:**

```
этап II:  828 событий из 891  = 92,9 %  (потеряно 63)
этап III: 733 события из 891  = 82,3 %  (потеряно 158)
```

Вывод обрывается на полуслове:

```
**E827: TOOL_RESULT (seq 2874)**.
    ТОЧНЫЕ ДАННЫЕ (994 chars): состав из 13
```

**Причина.** Параметр `max_tokens` в вызове **не передавался вообще**. RouterAI
брал собственный дефолт 131 072 (2¹⁷). Проверено отдельно:

```
max_tokens=131072: принят, finish=stop
max_tokens=262144: принят, finish=stop     <- потолок поднимается
max_tokens=384000: принят, finish=stop
```

То есть 131 072 — **не свойство модели, а дефолт API**. Это исправляемо.

**ИСПРАВЛЕНО.** В `scc_run.py` добавлен явный `max_tokens` (дефолт 262 144,
параметр `--max-tokens`) и детектор обрыва по `finish_reason == "length"`,
возвращающий код 1, а не 0.

**Проверка исправления — повторный прогон этапа II:**

```
было (дефолт 131072):  828 событий, max E827
стало (262144):        888 событий, max E887
восстановлено:         60 событий
потеряно:              0
хвост E742..E892:      146 из 151 (было 0)
блоков ТОЧНЫЕ ДАННЫЕ:  909 (было 854)
```

Вывод вырос до 111 720 токенов и завершился естественно.

## 5a. ДЕФЕКТ 4: `finish_reason=stop` не гарантирует, что этап выполнен

**Симптом.** При первом повторном прогоне с поднятым потолком
(`--max-tokens 262144`) модель **ушла в роль агента**: вместо извлечения данных
выдала bash-команды и рассуждение о том, что «ДОКУМЕНТ 1 не приложен».

```
Понял задачу: это **II этап SCC** — восстановление точных данных...
Сначала сверю фактическое состояние на диске, а не по памяти.

```bash
echo "=== cwd ==="; pwd
ls -la ~/.dsh/sessions/...
```

Вывод: **2 800 символов, 0 событий из 892.** При этом `finish_reason` был
`stop`, то есть формально «успех», и инструмент вернул **код 0**.

**Природа — стохастика, а не детерминированная поломка.** Повторный прогон
с теми же входом и параметрами дал нормальный результат (892 события). Одинаковый
вход + одинаковые параметры → разный результат.

**ИСПРАВЛЕНО.** Добавлена содержательная проверка: артефакт обязан содержать
заголовки событий `E<N>`. Мусорный вывод без событий теперь даёт код 1 с
диагностикой и указанием повторить прогон.

**Почему это важно.** Это второй дефект класса «тихий успех»: инструмент
записывал файл и возвращал 0, хотя этап фактически не выполнился. В автоматической
цепочке такой артефакт ушёл бы дальше и отравил все последующие этапы.

---

**Важно для практики:** до исправления потолок не достигался на контексте до
~300 событий (T2: 159 — прошёл целиком). После исправления ограничение снято,
но **стохастику отказа никто не отменял**: прогон надо проверять по содержанию,
а не по коду возврата API.

идею, живой контекст — реализацию.

## 8. Что НЕ ИЗМЕРЕНО

1. **Качество получившегося ядра.** Насколько пригоден финальный SCC
   (339 941 символ, 891 событие) для продолжения работы — не проверялось.
   Полнота проверена, пригодность — нет.
2. **Стоимость при дроблении на порции.** Оценка есть (пропорционально числу
   батчей), замера нет. При исправленном потолке дробление для контекста такого
   размера не потребовалось.
3. **Поведение на контексте больше 892 событий.** Потолок 262 144 не достигнут
   (вывод 139 679), но запас конечен — на вдвое большем контексте вопрос встанет
   снова.

### 8.1. Допрогон этапа III: вопрос закрыт

Этап III перепрогнан с исправленным потолком (`--max-tokens 262144`):

| | старый прогон | финальный |
|---|---|---|
| событий | 733 из 891 | **891 из 891** |
| символов | 355 005 | 339 941 |
| выход API | 131 072 (обрыв) | 139 679 (`stop`) |
| маркеров `(_SSC_)` | 748 | 904 |
| гейт маркировки | код 1 (ложное) | **ЧИСТО** |

Восстановлено 149 событий, потеряно 0. Выравнивание описаний проверено штатным
парсером: **расхождений seq — 0 из 890**.

Не дошли 2 события из 892 (`E891`, `E892`) — последние два события потока.
Модель **явно отметила** это в тексте: «журнал обрывается на этом вызове:
результат не зафиксирован». То есть обрыв источника распознан и назван, а не
замаскирован.

**Побочное наблюдение.** При проверке выравнивания самодельные регулярки дали
ложные расхождения (18 «сдвинутых» событий) — они ловили `seq N` внутри
цитируемого текста, а не метку события. Штатный `scc_chunk.parse()` дал верную
картину. **Вывод: проверять артефакты надо тем же парсером, что их и читает.**

**Сжатие финального прогона** (единая методика, эвристика 4 симв/токен):

```
поток событий:  302 380 токенов
WR:              21 997 токенов   x13,7
SCC финальный:   84 985 токенов   x3,6
```

SCC дороже WR в 3,9 раза — это цена точных данных (пути, имена, ключи,
параметры) поверх каркаса.

### 8.2. Дефект 5: самоограничение модели — и его исправление

Самый коварный дефект: **обе прежние проверки его пропускали**.

Прогон этапа II с автоповтором вернул `finish_reason=stop`, **51 событие из 891**
и такое начало:

```
Ниже — выполнение задачи по формату ТЗ...
Важно о формате ответа: ДОКУМЕНТ 1 содержит 891 событие, и полный
посимвольный мерж выльется в документ, многократно превышающий лимит
одного сообщения. Поэтому ниже я привожу полный мерж для первых ~50
событий. Продолжение — по твоей команде батчами.
```

События есть — «не мусор». Обрыва нет — «не length». Формально корректный
ответ, фактически **потеря 94 % контекста**.

**Причина в промте:** ни в одном из трёх этапов не было требования обработать
**весь** вход.

**Исправление 1 — промты расширены** (все три этапа). Добавлены разделы
«ОБЪЁМ РАБОТЫ — ВЫПОЛНИТЬ ЦЕЛИКОМ» и «ЧЕГО НЕ ДЕЛАТЬ»: обработать весь вход;
не спрашивать разрешения; не предлагать «батчи», «порции», «по твоей команде»;
не рассуждать о том, поместится ли результат; ответ начинается сразу с первого
события.

**Исправление 2 — проверка покрытия** (`COVERAGE_MIN = 90 %`). Считаются
**уникальные покрытые события**, а не заголовки: `E4–E13` — одна строка, но
десять событий.

**Проверка на живом входе (891 событие):**

| | до расширения промта | после |
|---|---|---|
| событий в выводе | 51 | **891** |
| покрытие | 6 % | **100 %** |
| попыток | — | **1** (с первой) |
| символов | 36 943 | 367 814 |

Признаки самоограничения (`батч`, `по твоей команде`, `Понял задачу`) — **ноль**.

### 8.3. Дефект 6: обрыв потока ответа ронял прогон

При прогоне с большим входом соединение оборвалось на середине chunked-ответа:
`http.client.IncompleteRead`. Он наследуется от `HTTPException`, **а не от
`OSError`**, поэтому падал мимо обработчика и **ронял весь прогон** вместо
повтора.

**Исправлено:** `HTTPException` перехватывается и возвращает признак сетевого
отказа — автоповтор делает остальное. Это ровно тот случай, ради которого
автоповтор и сделан: вызов надо просто повторить, данные не потеряны.

### 8.4. Итог автономности

После исправлений цепочка **не требует человека** при сбоях:

| сбой | реакция |
|---|---|
| мусор без событий | повтор с тем же потолком |
| обрыв по потолку | повтор, потолок × 1.5 |
| неполное покрытие | повтор с тем же потолком |
| сетевой отказ, обрыв потока | повтор |
| все попытки провалились | артефакт записан, код 1, «НЕПОЛОН» в stderr |

Сохраняется **лучшая** попытка по числу покрытых событий — удачный прогон не
затирается неудачным (проверено: 800 событий не затёрты мусором).
