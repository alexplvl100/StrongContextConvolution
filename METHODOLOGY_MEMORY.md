# METHODOLOGY_MEMORY — трёхуровневый механизм памяти

**Версия:** 2.3 · **Дата:** 2026-10-28
**Состояние:** ПРИНЯТ
**Реализация:** тестовая реализация
**Код:** [`_engine/memory/`](_engine/memory/)

Документ описывает, **где хранятся чанки** и **как они перемещаются** между
уровнями. Как чанк создаётся — в [`METHODOLOGY_CORE.md`](METHODOLOGY_CORE.md).
Как обрабатываются точные данные внутри чанка — в
[`METHODOLOGY_CAS.md`](METHODOLOGY_CAS.md). Что стоит **перед** памятью —
[`METHODOLOGY_HEAD.md`](METHODOLOGY_HEAD.md).

---

## 0. HEAD стоит перед памятью, но уровнем памяти НЕ является

**HEAD** — отдельная единица: служебный текст в самом начале контекста
(роль агента и инструкции доступа). Он **не сжимается** ядром, **не
обрабатывается** CAS и **не уходит** в архив (инвариант 8).

**Два канала.** В харнессе разделены системный контекст (постоянный: роль,
правила) и юзерконтекст (= короткая память). Через ядро SCC проходит **только
юзерконтекст**; системный контекст идёт в HEAD напрямую. Разделение
обеспечивается на конвертере журнала, а не изъятием из потока —
[`METHODOLOGY_HEAD.md`](METHODOLOGY_HEAD.md) §3.1.

```
┌──────────────────────────────────────────────┐
│ HEAD — не память: не сжимается, не выносится  │
├──────────────────────────────────────────────┤
│ СРЕДНЯЯ (стак чанков)                         │
├──────────────────────────────────────────────┤
│ КОРОТКАЯ (несжатый диалог)                    │
└──────────────────────────────────────────────┘
```

Уровней памяти **три** (короткая, средняя, долгая), и HEAD не четвёртый: у него
нет чанка, нет порога и нет перехода. Он описан отдельным документом.

## 1. Три уровня

### КОРОТКАЯ

| | |
|---|---|
| **что** | несжатая часть контекста в харнессе |
| **кто растит** | чат |
| **кто сжимает** | ядро SCC, по `threshold_compress` |
| **результат** | `chunk_{n+1}` (с постфиксом маркера), **неизменяем** |

Короткая память — самая актуальная и единственная **несжатая** часть контекста.
Она не имеет чанка: чанк появляется, когда короткая память сжимается.

### СРЕДНЯЯ

| | |
|---|---|
| **что** | стак `chunk_1..chunk_k`, который ещё помещается в харнесс |
| **кто двигает** | скрипты (без LLM): append, stack, обновление chain.json |
| **условие** | размер стака ≤ `threshold_archivist` |
| **в контексте** | **HEAD** + стак + короткая |

### ДОЛГАЯ

| | |
|---|---|
| **что** | те же чанки, вынесенные из контекста |
| **кто двигает** | скрипты (без LLM): вынос, инструкция, номер последнего чанка |
| **условие** | размер стака > `threshold_archivist` |
| **в контексте** | **HEAD** + короткая; содержимое — только через Архивариуса |

## 2. Переходы

```
короткая -> средняя:  ядро SCC по threshold_compress, создаёт chunk_{n+1}
средняя  -> долгая:   скрипт по threshold_archivist, выносит СТАРЕЙШИЙ чанк
долгая   -> средняя:  НЕ БЫВАЕТ (повторная свёртка запрещена; Архивариус только читает)
```

Переход «долгая → средняя» **отсутствует принципиально**. Чанк, вынесенный в
архив, возвращается в контекст только как ответ Архивариуса на запрос — но не
как элемент стака и **никогда** не проходит свёртку повторно.

**HEAD в переходах не участвует.** Он **не входит в поток событий** и потому в
свёртку не попадает: разделение каналов выполняется на конвертере журнала
(`--exclude-system`, [`METHODOLOGY_HEAD.md`](METHODOLOGY_HEAD.md) §3.1).

## 3. Схема уровней

```
┌─────────────────────────────────────────────────────────┐
│ ХАРНЕСС (то, что видит модель)                          │
│                                                          │
│   ┌─── HEAD (не память, не сжимается) ───┐              │
│   │  роль агента                          │              │
│   │  инструкция Архивариуса  <- если архив есть          │
│   │  инструкция CAS                       │              │
│   └───────────────────────────────────────┘              │
│   chunk_1 (_SSC_)                                        │
│   chunk_2 (_SSC_)             СРЕДНЯЯ: стак чанков        │
│   ...                                                    │
│   chunk_k (_SSC_)                                        │
│   ─────────────────────────                              │
│   несжатый диалог             КОРОТКАЯ                    │
│                                                          │
└─────────────────────────────────────────────────────────┘
                    │ вынос по threshold_archivist
                    ▼
┌─────────────────────────────────────────────────────────┐
│ АРХИВ (вне контекста)                                    │
│   chunk_1 (_SSC_)  ...  chunk_m (_SSC_)   ДОЛГАЯ          │
│   доступ: только через Архивариуса                       │
└─────────────────────────────────────────────────────────┘
```

Порядок внутри харнесса фиксирован: **сначала HEAD, затем стак, затем короткая
память**. Короткая всегда последняя — она самая актуальная. HEAD всегда первый —
он формирует поведение до первого шага.

## 4. Пороги

Два **разных** числа, оба в конфиге, не магические константы в коде:

| Порог | Что означает | Кто применяет |
|---|---|---|
| `threshold_compress` | объём короткой памяти, при котором пора сжимать | ядро SCC |
| `threshold_archivist` | размер стака, при котором пора выносить в архив | скрипт памяти |

**Почему это разные числа.** Сжатие короткой памяти и вынос стака в архив —
разные события с разными причинами. Первое происходит, когда диалог вырос;
второе — когда накопленные чанки перестают помещаться. Один порог на оба
означал бы, что архив начинается ровно тогда же, когда и первое сжатие, — то
есть архив был бы всегда пуст или всегда переполнен.

### 4.1. Пороги ВЫВОДЯТСЯ из рабочей зоны

Пороги **не задаются произвольно** — они вычисляются из окна модели. Обоснование:
симуляция [`_engine/tools/simulate_memory.py`](_engine/tools/simulate_memory.py),
проверено 21 тестом ([`_test/test_memory_stability.py`](_test/test_memory_stability.py)).

**Опасность фиксированного порога.** Если порог задан долей окна (как штатная
компакция DSH: 0.8·W), возможны два вырождения:

| Режим | Условие | Что происходит |
|---|---|---|
| **A** | порог на общий контекст, стак без ограничения | **короткая память душится**: чанки образуют геометрический ряд, сумма сходится ко **всей** зоне |
| **B** | порог на общий контекст, стак ограничен | контекст **переполняет** зону на один шаг: условие не знает о дискретности прироста |
| **C** | порог на короткую память, стак ограничен | **устойчив**: чанки одинаковы, зона не превышена |

**Математика режима A.** Сжатие берёт `c = D/r`, после чего свободное место
уменьшается: `D_new = D·(1−1/r)`. Место убывает геометрически, чанки образуют
ряд, сумма которого сходится к `D₀` — весь запас зоны уходит в стак.

**Устойчивое правило (режим C).**

```
Z = W · zone_ratio                     рабочая зона (доля окна)
S = (Z − HEAD) · r / (r + K + 1)       предел короткой памяти
T = S − step                           порог сжатия
T_arch = K·c + c/2,  где c = (T+step)/r    порог архивации
```

где `W` — окно модели, `r` — коэффициент сжатия ядра, `K` — чанков в средней
памяти, `step` — прирост короткой памяти за шаг диалога.

**Почему `K + 1`, а не `K`.** Вынос частичный (по одному чанку), поэтому стак
колеблется `N → N+1 → N`. В зону надо укладывать **максимум** `N+1` — разбор
ниже.

**Вычитание шага обязательно:** без него контекст выходит за зону на
`step·(1 + (K+1)/r)` — при шаге 5 000, K=2 и r=3,6 это 9 167 токенов.

**Вынос — ЧАСТИЧНЫЙ: уходит самый старый чанк, актуальные остаются.**

Прежняя реализация выносила **все** чанки средней памяти. Это проще, но
неправильно по смыслу: актуальные чанки — свежая история, и выносить их вместе
со старыми значит терять из контекста то, что ещё нужно. Теперь `move_to_long`
выносит **один** старейший чанк, а `evict_to_limit` повторяет вынос, пока стак
не уложится в порог.

**Почему в формуле `K + 1` слот.** Вынос по одному означает, что стак
колеблется: `N` → `N+1` (сработал порог) → `N` (вынесли старейший). В рабочую
зону надо укладывать **максимум**, то есть `N+1`:

```
HEAD + (K+1)·c + T <= Z
```

Отсюда порог сжатия `T = (Z − HEAD)·r/(r + K + 1) − step`.

**Порог архивации ставится на середину между `K` и `K+1` чанками:**
`T_arch = K·c + c/2`.

Почему не ровно `K·c`: `needs_archive` использует **строгое** `>`, а размеры
чанков близки, но не равны. Порог ровно `K·c` оказывается на границе, и вынос
срабатывает уже на K-м чанке — стак держит `K−1` вместо `K`. Замерено: при
пороге 269 343 и чанке 134 672 два чанка давали ровно порог, и в средней памяти
оставался **один** чанк; пик контекста был 62 % вместо 76 %.

**Сколько это даёт.** Частичный вынос позволяет использовать рабочую зону
полнее, чем полный (окно 1M, K=2, r=3,6):

| Вынос | Порог архивации | Пик контекста | Доля окна |
|---|---|---|---|
| полный (прежний) | `(K−1)·c` | 733 253 | 73 % |
| **частичный** | **`K·c + c/2`** | **756 162** | **76 %** |

Пик считается в момент **перед** сжатием: HEAD + стак из `K` чанков + короткая
на пороге. Число получено арифметикой по текущей формуле и совпадает с замером
симуляцией ([`_engine/tools/simulate_memory.py`](_engine/tools/simulate_memory.py)).

Разница не только в числах: при частичном выносе **актуальные чанки остаются в
контексте**, а при полном уходили в архив вместе со старыми.

**Пороги измеряют РАЗНОЕ** — `threshold_compress` это короткая память,
`threshold_archivist` это стак. Сравнивать их отношением `>` **нельзя**: они в
разных единицах. Содержательная проверка — `MemoryConfig.fits_zone(window)`:
вся память помещается в рабочую зону.

**Параметры по умолчанию** — в [`_engine/memory/config.py`](_engine/memory/config.py).
При известном окне используйте `MemoryConfig.for_window(window)`.

## 5. Оборот памяти: без LLM

Все перемещения чанков выполняются **скриптами**:

| Операция | Кто | LLM |
|---|---|---|
| изъятие чанков из короткой памяти перед свёрткой | скрипт | нет |
| стак чанков `chunk_1..chunk_n` | скрипт | нет |
| обновление последнего чанка | скрипт | нет |
| вынос в архив (старейшего чанка) | скрипт | нет |
| простановка инструкции Архивариуса с номером последнего чанка | скрипт | нет |
| сохранение состояния | скрипт | нет |

**Архивариус — агент с LLM, и он единственный в контуре ПАМЯТИ.** Он выполняет
разведку долгой памяти и информирование, отвечает на запросы основного агента.
Он **не переписывает и не сжимает** чанки — только читает.

**Чего Архивариус НЕ делает: он не работает с CAS.** Это не его область.
Точные данные (ссылки `CAS?{хеш}?`) агент получает **напрямую из CAS**, в обход
Архивариуса. Причина: Архивариус — агент с языковой моделью, а генерация
**пересказывает**; точное значение обязано возвращаться **побайтово**. Полное
разграничение — в [`METHODOLOGY_CAS.md`](METHODOLOGY_CAS.md) §7.1.

Уточнение важно потому, что здесь раньше стояла формулировка «Архивариус —
единственное место, где в контуре памяти нужен LLM», которую можно прочитать как
«всё, что нужно от памяти, идёт через Архивариуса». Это неверно: **два разных
канала доступа** — архив через Архивариуса, точные данные через CAS напрямую.

## 6. Инварианты

Формулировки дословные; ссылки на этот раздел из других документов
употребляются вместо повторения.

**1. Ядро SCC применяется ТОЛЬКО к короткой памяти.**

**2. Повторная свёртка чанков средней и долгой памяти НЕДОПУСТИМА.**

**3. Оборот средней/долгой памяти (изъятие чанков перед свёрткой, стак, обновление последнего чанка, простановка промта обращения к Архивариусу с номером последнего чанка, сохранение) — СТРОГО без LLM, скриптами.**

**4. Чанк неизменяем после записи: новое сжатие создаёт chunk_{n}, не перезаписывает старые.**

**5. Стак чанков — детерминированная функция от chunk_1..chunk_n.**

**6. chain.json — единственный источник правды о порядке чанков.**

**7. Архивариус — агент с LLM: разведка долгой памяти и информирование, выполнение запросов основного агента. Не переписывает и не сжимает чанки.**

**8. HEAD — отдельная единица: НЕ подвержен преобразованиям ни со стороны SCC, ни со стороны CAS. Системный контекст (роль) — отдельный канал и в юзерконтекст, идущий в ядро, не попадает; при отсутствии разделения каналов в харнессе разделение выполняется на конвертере журнала (`--exclude-system`).**

Инвариант 8 — про **HEAD**, который не является уровнем памяти (§0). Он
объявляется здесь, потому что описывает **границу между памятью и служебным
текстом**: ядро и CAS работают с памятью, и им запрещено касаться HEAD.
Разделение каналов и сборка HEAD — в [`METHODOLOGY_HEAD.md`](METHODOLOGY_HEAD.md) §3.

## 7. chain.json

Единственный источник правды о порядке чанков (инвариант 6). Лежит в
`runtime/dialogs/<dialog_id>/chain.json`. Формат:

```json
{
  "dialog_id": "example",
  "chunks": [
    {"n": 1, "level": "medium", "file": "chunks/chunk_0001.json"},
    {"n": 2, "level": "long",   "file": "chunks/chunk_0002.json"}
  ],
  "last_chunk": 2,
  "updated_at": "2026-10-25T00:00:00+00:00"
}
```

**Порядок — только по полю `n`.** Лексикографическая сортировка имён файлов
запрещена: `chunk_10` встал бы перед `chunk_2`, и хронология разрушилась бы.
Это ограничение задания и одновременно следствие инварианта 5: стак обязан
быть детерминированной функцией от номеров.

## 8. Структура данных диалога

```
runtime/dialogs/<dialog_id>/          <- НЕ в git (.gitignore)
├── chunks/
│   ├── chunk_0001.json               <- чанк по _engine/core/schemas/chunk.schema.json
│   ├── chunk_0002.json
│   └── ...
├── chain.json                        <- порядок и уровни (инвариант 6)
└── cas.db                            <- CAS точных данных
```

`runtime/` исключён из репозитория: это оперативные данные, они растут и у
каждого диалога свои. Схема структуры описана здесь, а не хранится файлами.

## 9. Замеры токенов по уровням

Сценарий: диалог из 40 сообщений, короткая память растёт и сжимается.
Способ подсчёта — **эвристика «4 символа = 1 токен»** (`_engine/memory/tokens.py`),
точность ±33 % (замерено: эвристика занижает). Все числа — приближение,
годное для сравнения уровней между собой, но не для прогноза стоимости.

| Момент | Короткая | Средняя | Долгая | HEAD | **В контексте** | Без памяти |
|---|---|---|---|---|---|---|
| шаг 10 | 2 500 | 0 | 0 | 2 008 | **4 508** | 2 500 |
| шаг 20 | 2 900 | 2 100 | 0 | 2 008 | **7 008** | 5 400 |
| шаг 30 | 3 100 | 4 200 | 0 | 2 008 | **9 308** | 8 100 |
| шаг 40 | 3 300 | 2 200 | 2 100 | 2 008 | **7 508** | 10 800 |
| шаг 50 | 3 500 | 4 300 | 2 100 | 2 008 | **9 808** | 13 500 |

**HEAD в таблице отдельной колонкой, потому что он не память** (§0). Он стоит
~2 008 токенов (роль ~1 405, инструкции ~602) и **не растёт**: служебный раздел
фиксирован, память вокруг него растёт и сжимается. Без HEAD сравнение было бы
нечестным: в реальном контексте он занимает место.

**Что показывает таблица.** После выноса в архив (шаг 40) контекст
**уменьшается**, хотя диалог продолжает расти: средняя память освобождает место,
а долгая в контекст не попадает. Без механизма памяти расход растёт линейно.

**Числа без HEAD неполны:** он добавляет постоянные ~2 008 токенов, из-за
которых на ранних шагах (10–20) механизм памяти оказывается **дороже** прямого
контекста. Выгода начинается, когда память экономит больше, чем стоит HEAD.

Подробный прогон с фактическими числами — в
[`_docs/measurements.md`](_docs/measurements.md).
