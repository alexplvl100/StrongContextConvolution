## 2. Метод изоляции — основа всей работы

### 2.1. `DSH_HOME` — переменная, а не константа

Проверено в `dsh-home-paths/lib`:

```js
const DSH_HOME_ENV = "DSH_HOME";
function resolveDshHome(configured, env = process.env) {
  return resolveRoot(configured, env, DSH_HOME_ENV, defaultDshHome);
}
```

Приоритет: явный путь → `$DSH_HOME` → `~/.dsh`. Значит **всё состояние
харнесса переезжает одной переменной окружения**.

### 2.2. Что переезжает в отдельный home

```
$DSH_HOME/
├── profiles/<имя>/      профиль: cordis.yml, cordis.patch.yml, package.json
├── sessions/            сессии — свои, рабочие не видны
├── storages/            хранилища
├── logs/                логи запуска
└── .credentials.yaml    ключи (копия, источник не меняется)
```

### 2.3. Практическая последовательность

```bash
# 1. отдельный home — рабочее развёртывание не участвует
export WORK=/tmp/scc_iso
mkdir -p $WORK/home

# 2. профиль из шаблона (имена: acp, headless, sdk, sdk-minimal, web)
DSH_HOME=$WORK/home dsh --from-default-profile headless --profile scc-test

# 3. ключи — КОПИЯ; исходный файл не открывается на запись
cp ~/.dsh/.credentials.yaml $WORK/home/.credentials.yaml

# 4. проверка конфигурации БЕЗ запуска
DSH_HOME=$WORK/home dsh --profile scc-test \
  --patch $WORK/method.patch.yml --dump-config > $WORK/dump.yml

# 5. прогон
DSH_HOME=$WORK/home ROUTERAI_API_KEY=... dsh --profile scc-test \
  --patch $WORK/method.patch.yml run "проверка"
```

**Шаг 4 — ключевой.** `--dump-config` собирает конфигурацию и печатает дерево,
ничего не монтируя. Большинство выводов ниже получено этим способом; запуск
делался только для финальной проверки.

### 2.4. Почему `headless`, а не `web`

Проверено `--dump-config`: в профиле `headless` строка `compaction-basic` лежит
**на верхнем уровне** дерева, а в `web` — **внутри пресета** `standard`.

**Следствие:** в `headless` строка адресуется патчем по `id`:

```
- id: compaction-basic
  config:
    thresholdRatio: 0.5
→ WARNING: []            предупреждений нет
→ thresholdRatio: 0.5    применилось
```

В `web` тот же патч даёт `patch: entry "compaction-basic" not found` — до
вложенной строки пресета патч не достаёт (подтверждает отчёт разведки §3.2).

**Поэтому разработка ведётся на `headless`:** там точка подключения открыта и
адресуется штатным механизмом. Перенос на `web` — отдельная задача (§8.3).

## 3. Метод: SCC как движок компакции

### 3.1. Что заменяется и зачем

Штатная компакция (`dsh-compaction-basic`) при срабатывании **пересказывает**
историю. Каждый пересказ теряет детали — измерено в `research/`: от первой
сводки к 83-й сохраняется **0 %** фактов.

SCC делает иначе: сжимает **один раз**, помечает результат и больше его не
пересматривает. Свежая часть сжимается отдельно, ядро переносится дословно.

**Цель внедрения:** при срабатывании компакции создавать **SCC-артефакт**, а не
пересказ.

### 3.2. Контракт, который надо реализовать

`dsh-compaction/lib/types/index.d.ts` — три обязательных метода:

| Метод | Роль | Что делает наш движок |
|---|---|---|
| `compactIfNeeded(agent, trigger, signal)` | **само условие** автокомпоновки | решает, пора ли; при `trigger: "pressure"` сравнивает с порогом |
| `compactNow(agent, signal, sourceCommandId)` | ручной запуск командой | тот же путь без проверки порога |
| `compactRegion(start, end, agent, signal)` | замена диапазона | выполняет поверхностную замену |

Регистрируется как `ctx.compaction`. **Сервис синглтон**: повторная регистрация
бросает `service "compaction" has been registered at <…>`. Поэтому базовая
строка обязательно отключается — «рядом» поставить нельзя.

### 3.3. Сборка патча: проверенные примитивы

Три примитива патча, все проверены `--dump-config`:

| Примитив | Запись | Результат |
|---|---|---|
| **Отключить** | `- id: compaction-basic`<br>`  disabled: true` | строка остаётся в дереве с `disabled: true` |
| **Переопределить конфиг** | `- id: compaction-basic`<br>`  config: {thresholdRatio: 0.5}` | `config` **заменяется целиком**, не сливается |
| **Добавить свою** | `- insert:`<br>`    - id: scc-compaction`<br>`      name: '/путь/index.js'` | строка добавляется в корень |

**Без `insert` новую строку добавить нельзя.** Проверены оба отказа: патч без
`id` даёт `patch: id is required for non-insert patches`, патч с неизвестным
`id` — `patch: entry "scc-compaction" not found`.

Рабочий `method.patch.yml`:

```yaml
# 1. отключить штатную компакцию (синглтон сервиса)
- id: compaction-basic
  disabled: true

# 2. добавить свой движок
- insert:
    - id: scc-compaction
      name: '/tmp/scc_iso/plugin/index.js'
      config:
        thresholdRatio: 0.7        # свой порог
        sccStage: 3                # сколько этапов SCC выполнять
```

Проверено: `WARNING: []` — предупреждений нет, `compaction-basic` отключён,
`scc-compaction` в дереве.

### 3.4. Каркас плагина

Лежит в [`plugin/`](plugin/) — показывает форму и точки входа. Форма модуля:
`export const name`, `export const inject`, `export function apply(ctx)`.

**Что уже есть:** регистрация сервиса, слушатель `agent/pre-step`, заготовка
`compactRegion`, описание вызова ядра SCC.

**Что не сделано:** фактическая связка «сессия → поток событий → SCC →
поверхностная замена», проверка сбалансированности границ, транзакционность.

### 3.5. Что нельзя забыть при замене движка

**Отключение `compaction-basic` ломает `command-compact`.** Проверено:

```
dsh: warning: 1 entry did not activate
command-compact (@deepseek-ai/dsh-command-compact): pending (waiting for service: compaction)
```

Команда `/compact` ждёт сервис `compaction`. Свой движок **обязан** его
предоставлять — иначе команда не активируется. Это не ошибка конфигурации, а
следствие синглтонности: убрав один сервис, надо дать взамен свой.

#### Ловушка в `inject`: плагин ждал сервис, который сам должен дать

**Живой урок 2026-10-26, найден прогоном.** В каркасе плагина стояло:

```js
export const inject = ['sessions', 'compaction', 'tokenMeter']   // НЕВЕРНО
```

Смысл `inject` — «какие сервисы мне нужны». Но наш движок обязан сервис
`compaction` **предоставить** (мы же отключили штатный, чтобы занять его место).
Получился замкнутый круг, и плагин не активировался вовсе:

```
scc-compaction (...): pending (waiting for service: compaction)
```

**Правило:** свой движок **не внедряет** `compaction` — он его **регистрирует**.
Внедрять нужно только то, чем движок пользуется (`sessions`, `tokenMeter`).

После исправления плагин активируется: в предупреждениях остаётся только
`command-compact`, и это ожидаемо для каркаса — он ещё не регистрирует сервис.

## 4. Точки подключения

### 4.1. Где именно меняется поведение

| Точка | Механизм | Применимость |
|---|---|---|
| **Условие автокомпоновки** | свой `CompactionEngine` как `ctx.compaction` | основной путь |
| **Только суммаризатор** | подкласс `BasicCompactionEngine`, override `summarize()` | если политика давления устраивает |
| **Перехват шага** | слушатель `agent/pre-step` (waterfall) | дополнение, не замена |
| **Замена диапазона** | `session.append(..., {surfaceOp:{op:'replace',…}})` | чем движок делает работу |
| **Сборка системного промта** | `system-prompt/assemble` (waterfall, authoritative) | если нужно менять сборку контекста |
| **Размещение HEAD** | `PromptSection` (не сжимается, текст может быть функцией) | роль и инструкции всегда видимы |

### 4.1a. HEAD: где он живёт в DSH

**Это ключевая точка для SCC.** При компакции роль агента теряется, если лежит
внутри первого чанка. Проверено в коде харнесса:

| Канал | Свойства | Годится для HEAD |
|---|---|---|
| `PromptSection` (`section`) | в системном промте; **не сжимается**; `text` может быть **функцией** | **да** |
| `PromptContext` (`context`) | «durable user-role snapshot»; попадает в историю, **может быть сжат** | **нет** |

**Подтверждения из README `dsh-compaction-basic`:**

* компакция **«cannot reduce the system prompt, tools, or session prefix»**;
* **«a system prompt at surface node 0 is never shadowed»**.

**Что это значит для плагина:**

1. HEAD регистрируется как `PromptSection` с `order` меньше, чем у остальных
   секций, — чтобы стоял первым.
2. `text` — **функция**, а не строка: инструкция Архивариуса содержит номер
   последнего чанка, который меняется при выносе.
3. **Изъятие HEAD из потока не требуется** — харнесс сам не пускает системный
   промт под замену. Но SCC-ядро работает с потоком событий и о DSH не знает:
   если HEAD попадёт в поток, ядро его сожмёт. Поэтому сборщик потока обязан
   **не включать HEAD** в то, что уходит в ядро.

Полное описание метода — [`METHODOLOGY_HEAD.md`](../../METHODOLOGY_HEAD.md).
Инвариант 8 (HEAD неприкосновенен) — в
[`METHODOLOGY_MEMORY.md`](../../METHODOLOGY_MEMORY.md) §6.

**Открытый вопрос для внедрения:** роль в DSH уже приходит через системный
промт, то есть её **не нужно извлекать** — достаточно, чтобы SCC-ядро её не
видело. Если же SCC применяется к потоку, где роль лежит в событиях (другой
харнесс), изъятие обязательно.

**Минимальный путь для первой итерации — override `summarize()`:** политика
давления (`compactIfNeeded`) остаётся штатной и проверенной, меняется только
**порождение сводки**. Меньше кода, меньше риска.

**Полный путь (свой движок)** нужен, если меняется само условие: когда
срабатывать и какой диапазон брать.

### 4.2. Правила поверхностной замены

Все проверяются синхронно при `append` (`dsh-session/lib/index.js`):

| Правило | Следствие |
|---|---|
| `startSeq`/`endSeq` — **более ранние** события | нельзя ссылаться на будущее |
| `sourceEventSeqs` покрывают **все** затеняемые узлы плотно | пропуск узла — ошибка |
| обе границы существуют в текущем surface, `start ≤ end` | иначе отказ |
| **узел 0 защищён**: `system/message` накрывается только `system/message` по этому узлу | системный промт одной операцией не переписать вместе с историей |
| замена `tool/result` меняет **только content** | метаданные править нельзя |
| границы **сбалансированы** по tool-парам | вызов ассистента обязан остаться с результатом |

**Последнее правило — источник ошибок номер один.** Диапазон, разрывающий пару
«вызов инструмента — результат», отвергается. Для проверки в харнессе есть
`toolPairingBalancedBefore` / `toolPairingBalancedAfter`.

### 4.3. Что при этом не меняется

* `core/` SCC — ядро работает как есть: оно автономно и о DSH не знает;
* текущая конфигурация харнесса — не открывается на запись;
* штатные механики (`token-meter`, `command-compact`) — остаются, им даётся сервис.

## 5. Конфигурация

### 5.1. Параметры компакции

Штатные (из `dsh-compaction-basic`, имена проверены в коде):

| Параметр | По умолчанию | Что значит |
|---|---|---|
| `thresholdRatio` | 0.8 | доля окна, при которой срабатывает давление |
| `headroomTokens` | 65 536 | запас под ответ |
| `retainRatio` | 0.16 | какую долю хвоста удержать несжатой |
| `maxTokens` | 65 536 | потолок вывода сводки |

**Важно:** `config` при патче **заменяется целиком**, а не сливается. Если
переопределить `thresholdRatio`, остальные параметры надо перечислить заново —
иначе они вернутся к встроенным значениям по умолчанию.

### 5.2. Свои параметры SCC

| Параметр | Смысл | Значение |
|---|---|---|
| `sccStage` | сколько этапов SCC выполнять | 3 (полный) или 1 (только WR) |
| `sccTimeoutMs` | таймаут на этап | не меньше 120 000 (§8.1) |
| `sccNoMarker` | без постфикса | `true` для транзитной схемы |

### 5.3. Провайдер модели

Для SCC нужен OpenAI-совместимый эндпоинт. Параметры в изолированном профиле:

```yaml
- id: llm-pi-ai
  config:
    providers:
      routerai:
        apiKeyEnv: ROUTERAI_API_KEY
        api: openai-completions
        baseURL: https://routerai.ru/api/v1
        models:
          - id: deepseek/deepseek-v4.1-flash
            contextWindow: 1000000

- id: agent-default-model
  config:
    provider: routerai          # ВНИМАНИЕ: два поля, а не одно
    model: deepseek/deepseek-v4.1-flash
```

**Ловушка, на которой спотыкаешься:** сначала было написано
`model: routerai/deepseek/deepseek-v4.1-flash` одним полем — сервис
`agentDefaultModel` не поднялся, плагин `headless-runner` ждал его, запуск
падал. Правильно — **два отдельных поля** `provider` и `model`.

## 6. Критерии готовности

| # | Критерий | Как проверяется | Состояние |
|---|---|---|---|
| 1 | Изоляция работает | изолированный прогон отвечает моделью | **выполнено** |
| 2 | Точка подключения адресуется | `--dump-config` без `not found` | **выполнено** |
| 3 | Отключение базовой работает | `disabled: true` в дереве | **выполнено** |
| 4 | Свой плагин добавляется | строка в дереве, `WARNING: []` | **выполнено** |
| 5 | Плагин активируется | нет `pending (waiting for service)` для нашего плагина | **выполнено** |
| 5a | Сервис `compaction` регистрируется | `command-compact` активируется | **не проверено** |
| 6 | SCC-артефакт создаётся при давлении | в сессии появилось `compaction/*` | **не проверено** |
| 7 | Точные данные не теряются | вопросник пригодности по артефакту | **не проверено** |
| 8 | Повторная свёртка не происходит | ядро переносится, не сжимается | **не проверено** |
| 9 | Рабочая конфигурация не тронута | даты файлов, GUI отвечает | **выполнено** |
| 10 | Откат работает | удаление каталога изолированного home | **выполнено** |

**Следующий шаг — критерий 5a:** зарегистрировать сервис `compaction` в движке.
Пока он не зарегистрирован, `/compact` не работает и в предупреждениях запуска
висит `command-compact: pending`. Это первое, что сломается при внедрении.

## 7. Откат

**Откат тривиален и полон**, потому что всё изолировано:

```bash
rm -rf /tmp/scc_iso          # удалить рабочее пространство эксперимента
```

**Что при этом теряется:** ничего из рабочего развёртывания — изолированный
home содержит только сессии эксперимента.

| Что откатывается | Действие | Последствие |
|---|---|---|
| Патч метода | убрать `--patch` из запуска | штатная компакция возвращается |
| Свой плагин | убрать `insert`-блок | строка исчезает из дерева |
| Эксперимент целиком | `rm -rf $WORK` | следов не остаётся |
| Рабочая конфигурация | **не трогалась** | откат не требуется |

**Оговорка для будущего внедрения в `web`:** правка профиля вне workspace
требует approvals или `danger-full-access`, а сессии и `runtime/` — данные,
которые нельзя восстановить. Перед переносом на рабочий профиль нужен снимок
`cordis.patch.yml`.

## 8. Ограничения

### 8.1. Три вызова модели на одну компакцию — дорого

**Измерено** на небольшом контексте (57 402 символа):

| Этап | Время |
|---|---|
| 1 (WR) | 30 с |
| 2 (WR_FILLED) | 40 с |
| 3 (SCC) | 78 с |
| **Итого** | **148 с** |

**Требование провайдера к инференс-эндпоинту — TTFT до 2–3 с.** Для внешнего
инференса SCC в текущем виде **не подходит**: 148 секунд только на сжатие.

**Для компакции внутри харнесса это допустимо:** она асинхронна, идёт в простое
агента (`compactNow` требует простоя) и не блокирует ответ пользователю. Но
таймауты по умолчанию надо поднять.

### 8.2. Экономика внутри одного запроса отрицательная

Сжатие стоит **40 622 токена** входа, экономит **10 450** на запросе. Окупается
с **4-го** запроса с тем же контекстом.

**Для компакции это работает**, потому что сжатая история переиспользуется всеми
последующими шагами диалога. Для разового запроса — убыточно.

### 8.3. Точка подключения в `web` закрыта

В рабочем профиле `web` компакция лежит **внутри пресета** `standard`, и патч
по `id` до неё не достаёт (подтверждено дважды — отчётом и собственным
экспериментом). Рабочий обход — переопределение строки `preset-standard`
**целиком** (`config.plugins` заменяется), но это:

* требует перечислить **все** плагины пресета, а не только изменяемые;
* хрупко: обновление харнесса перепишет пресет, и патч разойдётся с ним молча.

Поэтому метод разрабатывается в `headless`, где точка открыта.

### 8.4. Прочее

| Ограничение | Следствие |
|---|---|
| `config` заменяется целиком | при патче перечислять все параметры |
| Узел 0 защищён | системный промт нельзя накрыть вместе с историей |
| Баланс tool-пар обязателен | диапазон, разрывающий пару, отвергается |
| `command-compact` зависит от сервиса | свой движок обязан предоставить `compaction` |
| Правка профиля вне workspace | требует approvals при переносе на рабочий профиль |
| Живое применение | патч профиля подхватывается HMR; смена плагина, вероятно, требует новой сессии — **не проверено** |

### 8.5. Чего этот документ не утверждает

1. **Что SCC-компакция лучше штатной.** Пригодность ядра измерена отдельно
   (`research/R-SCC-03`), но **в режиме компакции DSH не проверялась**.
2. **Что производительность достаточна.** 148 с измерены на CLI-прогоне; внутри
   плагина цифры будут иными — не измерялось.
3. **Что метод переносится на `web` без изменений.** Точка подключения там
   закрыта, нужен другой путь монтирования.
4. **Что плагин работоспособен.** В репозитории каркас, а не реализация.
