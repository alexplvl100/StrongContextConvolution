# Замеры расхода токенов по уровням памяти

**Дата:** 2026-10-28
**Инструмент:** [`_engine/tools/measure_memory.py`](../_engine/tools/measure_memory.py)
**Воспроизведение:** `python3 _engine/tools/measure_memory.py --window 262144 --steps 3000`

---

## 0. Почему этот документ переписан

Прежняя редакция (2026-10-25) считалась на **фиксированных порогах**
12 000 / 18 000 токенов. Эти числа **больше не существуют**: с версии 0.15
пороги **выводятся** из рабочей зоны окна модели
([`METHODOLOGY_MEMORY.md`](../METHODOLOGY_MEMORY.md) §4.1).

**Инструмент замера при этом был сломан**: он импортировал удалённые константы
`DEFAULT_THRESHOLD_COMPRESS` / `DEFAULT_THRESHOLD_ARCHIVIST` и падал с
`ImportError`. Таблица поэтому **устарела молча** — её нечем было пересчитать.
Это и есть живой урок: **документ с числами устаревает вместе с инструментом**,
и обнаруживается это только запуском.

Инструмент исправлен: пороги берутся через `derive_thresholds(window)`, окно
задаётся флагом `--window`.

**Что изменилось по существу, а не по числам:**

| | Прежняя редакция | Сейчас |
|---|---|---|
| Пороги | фиксированные 12 000 / 18 000 | **выводятся из окна** |
| Полный цикл (до архива) | 120 шагов | **615 шагов** (окно 262 144) |
| Экономия | ×15,6 — как **одно число** | **растёт с длиной сессии**: ×3,6 → ×21,5 |
| Контекст | не ограничен явно | **ограничен**: ≤73 % окна |

## 1. Чем считали токены — обязательно к указанию

**Эвристика «4 символа = 1 токен»** ([`_engine/memory/tokens.py`](../_engine/memory/tokens.py)).

Точность ограничена, и это замерено: на живой сессии эвристика дала 302 380
токенов там, где API насчитал **401 428** — то есть **занижает примерно на
треть**. Причина в том, что код, пути и JSON токенизируются плотнее: один токен
занимает 2–3 символа, а не 4.

**Что из этого следует:**

* числа годны для **сравнения уровней и режимов между собой** — систематическая
  ошибка сокращается;
* числа **не годны для прогноза стоимости** — реальный счёт будет выше примерно
  на треть;
* точный токенизатор модели в проекте не подключён.

## 2. Параметры сценария

| Параметр | Значение | Откуда |
|---|---|---|
| Окно модели | 262 144 | `--window`; вывод порогов |
| Шагов диалога | 3 000 | выбрано так, чтобы прошло **несколько** циклов архивации |
| Символов на шаг | 2 400 | средний шаг живой сессии (команда плюс вывод) |
| **Коэффициент сжатия** | **×3,6** | замерено на живой сессии для **SCC** |
| Порог сжатия | **122 597** ток | выведен из окна |
| Порог архивации | **85 136** ток | выведен из окна |
| Размер чанка | ~34 055 ток | порог сжатия ÷ 3,6 |
| Объём инструкции архива | ~253 ток | текст из `_engine/memory/long.py` |

**Про коэффициент сжатия.** Замерено два разных числа: WR (каркас без данных)
сжимает ×13,7, а SCC (каркас **плюс точные данные**) — только ×3,6. Чанк по
схеме хранит данные, поэтому верен именно ×3,6. Взять ×13,7 значило бы занизить
объём чанков вчетверо и получить неверную картину.

**Пороги выведены, а не выбраны.** Формула
`T = (Z − HEAD)·r/(r + K + 1) − step` при окне 262 144 даёт 122 597. Отсюда:

```
порог сжатия 122 597 ток = 490 388 симв
первое сжатие на шаге 490 388 / 2 400 ≈ 205
размер чанка 34 055 ток
порог архива 85 136 ток = 2,5 чанка
```

**Следствие, которого не было в прежней редакции:** при выведенных порогах
сценарий на **140 шагов не доходит даже до первого сжатия**. Прежняя таблица
показывала переходы на шагах 20 и 120 именно потому, что пороги были малы.
Это не «ухудшение»: пороги теперь согласованы с окном, а не подобраны под
удобную демонстрацию.

## 3. Основная таблица

Окно 262 144, 3 000 шагов по 2 400 символов. Показаны характерные точки:
срабатывания порогов и конец.

| шаг | короткая | средняя | долгая | инстр. | **в контексте** | без памяти |
|---|---|---|---|---|---|---|
| 1 | 600 | 0 | 0 | 0 | **600** | 600 |
| 205 | 0 | 34 195 | 0 | 0 | **34 195** | 123 000 |
| 410 | 0 | 68 391 | 0 | 0 | **68 391** | 246 000 |
| **615** | 0 | 68 391 | 34 195 | 253 | **68 644** | 369 000 |
| 1 230 | 0 | 68 391 | 136 782 | 253 | **68 644** | 738 000 |
| 2 460 | 0 | 68 391 | 341 955 | 253 | **68 644** | 1 476 000 |
| 3 000 | 78 065 | 68 391 | 410 346 | 253 | **146 709** | 1 800 000 |

**Что видно.** С шага 615 и до 2 460 контекст **не растёт вообще**: 68 644
токена, хотя архив вырос с 34 195 до 341 955 — **в десять раз**. Диалог
продолжается, а занимаемое место стоит на месте. Это и есть смысл долгой
памяти: данные не потеряны, но перестали занимать контекст.

Всплеск на шаге 3 000 — короткая память растёт заново после сжатия; это
**пилообразный** рост, а не линейный, и он ограничен порогом.

## 4. Границы контекста — главный результат

**Контекст ограничен сверху.** Максимум за прогон:

| Величина | Токенов | Доля окна |
|---|---|---|
| Максимум памяти в контексте | **191 146** | 72,9 % |
| Аналитическая граница `T + K·c + инстр` | 190 706 | 72,7 % |
| С учётом HEAD (~2 008) | 192 714 | **73,5 %** |

Аналитическая граница совпадает с замером: **модель порогов верна**.

```
максимум = короткая на пороге + стак из K чанков + инструкция
         = 122 597 + 68 110 + 253 ≈ 190 960
```

**Почему это важно.** Прежняя редакция показывала «экономию ×15,6» как
**свойство механизма**. На деле это была случайная точка конкретной длины
сессии. Правильная формулировка:

> **Контекст ограничен рабочей зоной, поэтому экономия растёт с длиной сессии
> без предела** — числитель (без памяти) растёт линейно, знаменатель
> (в контексте) стоит на месте.

## 5. Экономия растёт с длиной сессии

| Шаг | В контексте | Без памяти | Экономия |
|---|---|---|---|
| 205 | 34 195 | 123 000 | ×3,60 |
| 615 | 68 644 | 369 000 | ×5,38 |
| 1 230 | 68 644 | 738 000 | ×10,75 |
| 2 460 | 68 644 | 1 476 000 | ×21,50 |

**Число «×15,6» из прежней редакции было не свойством механизма, а точкой на
этой прямой.** Оно зависело только от того, сколько шагов успели прогнать.

На коротких сессиях картина обратная: на шаге 205 экономия лишь ×3,6, а с
учётом HEAD (~2 008 постоянно) — ещё ниже. **Выгода начинается, когда память
экономит больше, чем стоит HEAD.**

## 6. Итог

| | токенов |
|---|---|
| Максимум памяти в контексте | **191 146** |
| HEAD (постоянно, не растёт) | ~2 008 |
| **Потолок контекста** | **~193 000** (73,5 % окна) |
| Без механизма памяти на шаге 3 000 | **1 800 000** |
| Экономия на шаге 3 000 | **×12,3** |
| Экономия на шаге 2 460 | **×21,5** |

**Ключевое свойство — не «экономия в N раз», а ОГРАНИЧЕННОСТЬ контекста.**
Именно она делает длинную сессию возможной: без памяти контекст упёрся бы в
окно модели и работа остановилась бы.

## 7. Что моделировалось, а что нет

**Моделировалось:** рост контекста, срабатывание обоих порогов, переходы
уровней, объём инструкции архива, накопление чанков, повторные циклы архивации
(до 12 выносов).

**Не моделировалось:**

* **содержание сжатия** — сжатие имитируется коэффициентом, а не вызовом ядра:
  замер должен быть детерминированным и не зависеть от LLM;
* **работа CAS** — он уменьшает объём чанков, поэтому оценка
  **консервативна**: с CAS экономия была бы выше;
* **поведение агента** — замерялся объём контекста, а не качество работы по нему.
  Пригодность ядра измерена отдельно ([`_research/R-SCC-03`](../_research/R-SCC-03_пригодность.md));
* **HEAD** — в таблицах он указан отдельно и в сумму памяти не входит (инвариант 8).

## 8. Ограничения замера

1. **Один сценарий.** Шаг фиксирован (2 400 символов) и однороден. Реальный
   диалог чередует короткие реплики и длинные выводы команд.
2. **Коэффициент постоянен.** В реальности он зависит от однородности материала:
   от ×3,6 на разнородной работе до ×131 на однотипных повторах.
3. **Модель роста линейна.** Всплески (гигантский вывод команды) дали бы
   ступеньку вместо плавной линии.
4. **Одно окно.** Проверено 262 144. При окне 1 000 000 пороги вчетверо больше,
   и пропорции сохраняются, но замер не повторялся на всех размерах.
5. **Эвристика токенов занижает на треть** (§1) — абсолютные числа не годны
   для прогноза стоимости.
