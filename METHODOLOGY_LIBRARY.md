# METHODOLOGY_LIBRARY — глоссарий точных данных

**Версия:** 1.0 · **Дата:** 2026-10-25
**Статус:** интерфейс реализован, полная интеграция отложена
**Код:** [`memory/glossary.py`](memory/glossary.py)

> **Термин.** В проекте используется **«глоссарий»** — везде: в коде
> (`memory/glossary.py`), в схеме (`glossary_refs`), в методологии. Синоним
> «библиотека» сохранён только в имени этого файла, потому что так задан
> постановкой. При расхождении формулировок верен термин «глоссарий».

Документ описывает **обработку точных данных внутри чанка**. Когда чанк
создаётся — в [`METHODOLOGY_CORE.md`](METHODOLOGY_CORE.md). Где он хранится — в
[`METHODOLOGY_MEMORY.md`](METHODOLOGY_MEMORY.md).

---

## 1. Зачем это нужно

Ядро отсеивает стохастику, но **точные данные оно сохраняет** — и правильно
делает: пути, идентификаторы и числа нужны для работы. Проблема в другом: одни
и те же значения **повторяются** в чанках, а чанки копятся. Один и тот же путь,
упомянутый двадцать раз, занимает место двадцать раз.

Глоссарий решает это так: повторяющееся значение заменяется **ссылкой на
хеш**, а оригинал хранится один раз в базе.

```
было:   ~/.dsh/profiles/web/cordis.patch.yml    (41 символ, повторяется)
стало:  LB?a1b2c3d4?                                (13 символов, один раз в БД)
```

## 2. Что считается точными данными

Список **открытый**: правило «похоже на точное значение» оценочное, поэтому
перечень фиксирует то, что обрабатывается в тестовой реализации, и может
расширяться.

| Класс | Пример | Обрабатывается |
|---|---|---|
| **Пути файлов** | `~/.dsh/profiles/web/cordis.patch.yml` | да |
| **Идентификаторы** | `alexplvl100/MultiAgentDSH`, `deepseek-v4.1-flash` | да |
| **Хеши** | `af3dba1cc7afffee8b7c4f485ee5afcc…` (64 hex) | да |
| **Числовые параметры** | `262144`, `65536`, `thresholdRatio = 0.8` | да |
| **Даты и время** | `2026-10-25T00:00:00+00:00`, `2026-10-25` | да |
| **Суммы и величины** | `154 026 токенов`, `688 КБ` | частично |
| **Имена файлов** | `chunk_0001.json`, `scc_run.py` | да |
| **Адреса и URL** | `baseURL` провайдера | да |
| **Обычный текст** | «прочитать 20 файлов», «сжать контекст» | **нет** |

**Что НЕ обрабатывается:** связный текст, описания, рассуждения. Замена
текстовых фраз на хеши разрушила бы читаемость чанка, а выгоды не дала бы —
они не повторяются дословно.

**Отдельно про числа.** Короткие числа (`0`, `1`, `20`) не заменяются: ссылка
`LB?a1b2c3d4?` длиннее самого значения, и замена даёт рост, а не экономию.
Порог минимальной длины — параметр `glossary_min_length` в конфиге.

## 3. Формат ссылки в чанке

```
LB?{хеш}?
```

Примеры:

```
LB?a1b2c3d4?
LB?7f3e9c01?
```

`LB` — от «library» (имя файла методологии). Восемь шестнадцатеричных символов
— ровно столько, сколько даёт 32 бита, то есть около 4 миллиардов значений.

**Хеш — ключ базы**, где хранится оригинал строки. Не «похожее значение», а
именно та строка, которую заменили: восстановление обязано быть дословным.

## 4. Когда формируется

**В момент свёртки, ПОСЛЕ работы ядра.**

```
1. ядро SCC сжимает короткую память       -> чанк с точными данными
2. глоссарий проходит по чанку             -> заменяет повторы на LB?{хеш}?
3. оригиналы пишутся в базу
4. glossary_refs чанка заполняется списком хешей
```

**Почему после, а не во время.** Ядро — проход языковой модели; глоссарий —
детерминированная обработка текста. Смешивать их нельзя: ядро должно закончить
и зафиксировать чанк, иначе глоссарий работал бы по нестабильному входу.

**Формирование хеша, замена в чанке и запись в базу — БЕЗ LLM.** Это
продолжение инварианта 3 из [`METHODOLOGY_MEMORY.md`](METHODOLOGY_MEMORY.md) §6:
в контуре памяти языковая модель не участвует.

## 5. Алгоритм хеша

**Стабильность обязательна: одна и та же строка → один и тот же хеш.** Иначе
смысл ссылки теряется, и восстановление станет невозможным.

```
hash = sha256(нормализованная_строка)[:8]
```

**Нормализация** (иначе один и тот же путь в разном обрамлении даст разные хеши):

| Что делается | Зачем |
|---|---|
| удаление обрамляющих пробелов | `" путь "` и `"путь"` — одно |
| удаление обрамляющих кавычек и бэктиков | `` `путь` `` и `путь` — одно |
| схлопывание внутренних пробелов | случайные двойные пробелы |
| приведение регистра **не** делается | в путях регистр значим |

**Коллизии.** Восемь hex-символов дают 2³² значений. Вероятность коллизии
растёт как √(2³²) ≈ 77 000 уникальных строк — на практике диалога это
достижимо теоретически, поэтому:

* **при записи** проверяется, не занят ли хеш другой строкой;
* если занят — берётся следующий свободный хеш (`hash+1` по модулю 2³²);
* **конфликт фиксируется в лог**, потому что означает рост базы выше расчётного.

Обратное направление (по хешу получить строку) однозначно: хеш — ключ, а не
вычисляемое значение.

## 6. Где хранится база

```
runtime/dialogs/<dialog_id>/glossary.db
```

SQLite, **по базе на диалог**. Причины:

1. **Изоляция.** Диалоги независимы: удаление одного не задевает другие.
2. **Переносимость.** Диалог можно скопировать целиком — вместе с его
   глоссарием.
3. **Размер.** База растёт с диалогом, а не со всей системой.

Схема:

```sql
CREATE TABLE glossary (
    hash       TEXT PRIMARY KEY,   -- 8 hex-символов
    value      TEXT NOT NULL,      -- оригинал строки, дословно
    first_seen TEXT NOT NULL,      -- ISO 8601, когда добавлено
    uses       INTEGER DEFAULT 1   -- сколько раз встретилось
);
```

`runtime/` исключён из репозитория (`.gitignore`): база — оперативные данные.

## 7. Как агент получает оригинал

**Через Архивариуса.**

Основной агент видит в чанке ссылку `LB?a1b2c3d4?` и, если значение нужно,
запрашивает его у Архивариуса. Тот читает базу и возвращает оригинал.

**Почему не напрямую.** Архивариус — единственная точка доступа к долгой памяти
(инвариант 7). Прямой доступ агента к базе создал бы второй путь к тем же
данным, а значит — два источника правды о том, что было в архиве. Кроме того,
прямой SQL-доступ из модели означает выдачу ей произвольных запросов к базе,
что выходит за рамки задачи.

**Что это даёт на практике.** Ссылки в чанке дешёвы: 13 символов вместо 41.
Если значение не нужно — за него не платят вообще. Если нужно — Архивариус
вернёт его за один запрос.

## 8. Статус реализации

| Часть | Состояние |
|---|---|
| Интерфейс (`memory/glossary.py`) | **реализован**: хеш, нормализация, замена, SQLite |
| Тесты | **зелёные**: детерминизм хеша, round-trip замены, коллизии |
| Интеграция с ядром при свёртке | **НЕ реализована** — отложено |
| Запрос оригинала через Архивариуса | **НЕ реализован** — Архивариус сам в разработке |

То есть **обработка значений работает и проверена**, но автоматической связки
«ядро создало чанк → глоссарий обработал» пока нет: сейчас глоссарий вызывается
явно. Это первое, что нужно доделать при следующей итерации.
