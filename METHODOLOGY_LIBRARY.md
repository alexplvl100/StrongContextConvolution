# METHODOLOGY_LIBRARY — CAS: хранилище точных данных

**Версия:** 1.0 · **Дата:** 2026-10-25
**Статус:** интерфейс реализован, полная интеграция отложена
**Код:** [`memory/cas.py`](memory/cas.py)

> **Термин УТВЕРЖДЁН: CAS (content-addressed store).**
>
> Ранее документ называл механизм «глоссарием» — это было **неверно по сути**.
> Глоссарий даёт определения терминов; здесь толкования нет, значение
> возвращается дословно. Библиотека предполагает каталог и классификацию
> объектов с самостоятельной ценностью; здесь плоская таблица «адрес → строка».
>
> Точное имя — **CAS**: адрес вычисляется из содержимого
> (`sha256(value)[:8]`), восстановление побайтовое, смысл значения для
> хранилища безразличен. Именно так это и работает в `memory/cas.py`.
>
> **Имя файла `METHODOLOGY_LIBRARY.md` оставлено** исторически — оно задано
> постановкой и на него есть ссылки. Термин в тексте — только **CAS**.
>
> **Токен ссылки `LB?`** тоже оставлен: он присутствует во всех ранее созданных
> артефактах, и переименование разошлось бы с накопленной историей.

Документ описывает **обработку точных данных внутри чанка**. Когда чанк
создаётся — в [`METHODOLOGY_CORE.md`](METHODOLOGY_CORE.md). Где он хранится — в
[`METHODOLOGY_MEMORY.md`](METHODOLOGY_MEMORY.md).

## 1. Зачем это нужно

Ядро отсеивает стохастику, но **точные данные оно сохраняет** — и правильно
делает: пути, идентификаторы и числа нужны для работы. Проблема в другом: одни
и те же значения **повторяются** в чанках, а чанки копятся. Один и тот же путь,
упомянутый двадцать раз, занимает место двадцать раз.

CAS решает это так: повторяющееся значение заменяется **ссылкой на
хеш**, а оригинал хранится один раз в базе.

```
было:   ~/.dsh/profiles/web/cordis.patch.yml    (41 символ, повторяется)
стало:  LB?a1b2c3d4?                                (13 символов, один раз в БД)
```

## 2. Что считается точными данными

Список **открытый**: правило «похоже на точное значение» оценочное, поэтому
перечень фиксирует то, что обрабатывается в тестовой реализации, и может
расширяться.

| Класс | Пример | Обрабатывается |
|---|---|---|
| **Пути файлов** | `~/.dsh/profiles/web/cordis.patch.yml` | да |
| **Идентификаторы** | `alexplvl100/MultiAgentDSH`, `deepseek-v4.1-flash` | да |
| **Хеши** | `af3dba1cc7afffee8b7c4f485ee5afcc…` (64 hex) | да |
| **Числовые параметры** | `262144`, `65536`, `thresholdRatio = 0.8` | да |
| **Даты и время** | `2026-10-25T00:00:00+00:00`, `2026-10-25` | да |
| **Суммы и величины** | `154 026 токенов`, `688 КБ` | частично |
| **Имена файлов** | `chunk_0001.json`, `scc_run.py` | да |
| **Адреса и URL** | `baseURL` провайдера | да |
| **Обычный текст** | «прочитать 20 файлов», «сжать контекст» | **нет** |

**Что НЕ обрабатывается:** связный текст, описания, рассуждения. Замена
текстовых фраз на хеши разрушила бы читаемость чанка, а выгоды не дала бы —
они не повторяются дословно.

**Отдельно про числа.** Короткие числа (`0`, `1`, `20`) не заменяются: ссылка
`LB?a1b2c3d4?` длиннее самого значения, и замена даёт рост, а не экономию.
Порог минимальной длины — параметр `cas_min_length` в конфиге.

## 3. Формат ссылки в чанке

```
LB?{хеш}?
```

Примеры:

```
LB?a1b2c3d4?
LB?7f3e9c01?
```

`LB` — от «library» (имя файла методологии). Восемь шестнадцатеричных символов
— ровно столько, сколько даёт 32 бита, то есть около 4 миллиардов значений.

**Хеш — ключ базы**, где хранится оригинал строки. Не «похожее значение», а
именно та строка, которую заменили: восстановление обязано быть дословным.

## 4. Когда формируется

**В момент свёртки, ПОСЛЕ работы ядра.**

```
1. ядро SCC сжимает короткую память       -> чанк с точными данными
2. CAS проходит по чанку             -> заменяет повторы на LB?{хеш}?
3. оригиналы пишутся в базу
4. cas_refs чанка заполняется списком хешей
```

**Почему после, а не во время.** Ядро — проход языковой модели; CAS —
детерминированная обработка текста. Смешивать их нельзя: ядро должно закончить
и зафиксировать чанк, иначе CAS работал бы по нестабильному входу.

**Формирование хеша, замена в чанке и запись в базу — БЕЗ LLM.** Это
продолжение инварианта 3 из [`METHODOLOGY_MEMORY.md`](METHODOLOGY_MEMORY.md) §6:
в контуре памяти языковая модель не участвует.

Реализовано в [`memory/linking.py`](memory/linking.py): функция `link_cas`
принимает чанк и CAS, возвращает обработанный чанк. Отсутствие LLM в этом
модуле проверяется тестом — разбором исходника через AST.

## 5. Алгоритм хеша

**Стабильность обязательна: одна и та же строка → один и тот же хеш.** Иначе
смысл ссылки теряется, и восстановление станет невозможным.

```
hash = sha256(нормализованная_строка)[:8]
```

**Нормализация** (иначе один и тот же путь в разном обрамлении даст разные хеши):

| Что делается | Зачем |
|---|---|
| удаление обрамляющих пробелов | `" путь "` и `"путь"` — одно |
| удаление обрамляющих кавычек и бэктиков | `` `путь` `` и `путь` — одно |
| схлопывание внутренних пробелов | случайные двойные пробелы |
| приведение регистра **не** делается | в путях регистр значим |

**Коллизии.** Восемь hex-символов дают 2³² значений. Вероятность коллизии
растёт как √(2³²) ≈ 77 000 уникальных строк — на практике диалога это
достижимо теоретически, поэтому:

* **при записи** проверяется, не занят ли хеш другой строкой;
* если занят — берётся следующий свободный хеш (`hash+1` по модулю 2³²);
* **конфликт фиксируется в лог**, потому что означает рост базы выше расчётного.

Обратное направление (по хешу получить строку) однозначно: хеш — ключ, а не
вычисляемое значение.

## 6. Где хранится база

```
runtime/dialogs/<dialog_id>/cas.db
```

SQLite, **по базе на диалог**. Причины:

1. **Изоляция.** Диалоги независимы: удаление одного не задевает другие.
2. **Переносимость.** Диалог можно скопировать целиком — вместе с его
   CAS.
3. **Размер.** База растёт с диалогом, а не со всей системой.

Схема:

```sql
CREATE TABLE cas (
    hash       TEXT PRIMARY KEY,   -- 8 hex-символов
    value      TEXT NOT NULL,      -- оригинал строки, дословно
    first_seen TEXT NOT NULL,      -- ISO 8601, когда добавлено
    uses       INTEGER DEFAULT 1   -- сколько раз встретилось
);
```

`runtime/` исключён из репозитория (`.gitignore`): база — оперативные данные.

## 7. Как агент получает оригинал — НАПРЯМУЮ из CAS

**Основной агент обращается к CAS напрямую, вызовом функции. Обход Архивариуса
ОБЯЗАТЕЛЕН.**

```
агент видит в чанке ссылку  LB?a1b2c3d4?
        |
        +--> resolve_many([хеши])  -> словарь {хеш: оригинал}   ПРЯМОЙ ВЫЗОВ
        |
        +--> Архивариус НЕ участвует в этом пути
```

### 7.1. Почему напрямую, а не через Архивариуса

**Архивариус — агент с языковой моделью.** Любой его ответ проходит через
генерацию, а генерация **пересказывает**. Точное значение при этом искажается:
путь становится «похожим», хеш — «приблизительно верным», число — округлённым.

Для долгой памяти это допустимо: там нужно понимание, что было. Для точных
данных — **недопустимо**: смысл CAS в том, что значение возвращается
**побайтово**. Поэтому путь к точным данным не проходит ни через одну модель.

Разграничение простое:

| Что нужно | Откуда | Почему так |
|---|---|---|
| «Что происходило в архиве» | **Архивариус** (LLM) | нужен пересказ и обобщение |
| «Что это за точное значение» | **CAS напрямую** | нужна дословность, пересказ вреден |

### 7.2. Инструменты доступа

Модуль [`memory/cas.py`](memory/cas.py):

| Функция | Что делает |
|---|---|
| `resolve_many([хеши])` | словарь `{хеш: оригинал}` **одним** SQL-запросом |
| `restore(хеш)` | оригинал по одному хешу |
| `references_in(текст)` | список ссылок в чанке, в порядке появления, без повторов |

`resolve_many` — основной путь: список ссылок в чанке обычно длиннее одной, и
разрешать их поштучно значило бы делать лишние обращения к диску.

**Если хеш не разрешился** — его просто нет в результате. Подставить пустое или
правдоподобное значение означало бы потерять данные незаметно; отсутствие в
ответе видно, и агент обязан сказать об этом прямо.

### 7.3. Промт доступа — обязательная часть контекста

Агент не знает заранее, что такое `LB?{хеш}?`. Без объяснения ссылка выглядит
как мусор, и первая реакция будет «данные потеряны». Поэтому в контекст
ставится **промт CAS**, и его место строго определено:

```
+----------------------------------------------+
| [ промт Архивариуса ]  доступ к архиву чанков |
| [ ПРОМТ CAS ]          доступ к точным данным |  <- ЭТОТ БЛОК
| [ чанки ]                                     |
| [ короткая память ]                           |
+----------------------------------------------+
```

**После промта Архивариуса и перед чанками.** Две причины:

1. **Перед чанками** — агент читает контекст сверху вниз. Инструкция, стоящая
   после чанков, попадёт в поле зрения уже после того, как он наткнётся на
   непонятные ссылки.
2. **После промта Архивариуса** — сначала описывается доступ к архиву, затем к
   точным данным. Порядок отражает приоритет: архив даёт контекст, CAS — детали.

Промт формируется [`memory/cas_prompt.py`](memory/cas_prompt.py),
`build_cas_prompt()`. Он содержит три обязательных части:

* **условие** — что означает `LB?{хеш}?` и почему это не потеря данных;
* **порядок обращения** — какие функции вызывать и в каком порядке;
* **запрет** — не выводить ссылку как значение, не догадываться, не просить
  Архивариуса о расшифровке, не подставлять правдоподобное при неудаче.

**При нуле ссылок промт не ставится вовсе.** Упоминать механизм, которым не
воспользуются, значит занимать контекст впустую — а вся задача CAS в его
экономии.

### 7.4. Что это даёт на практике

| | |
|---|---|
| Ссылка в чанке | 13 символов вместо десятков |
| Значение не нужно | за него **не платят вообще** |
| Значение нужно | один вызов `resolve_many` на все ссылки |
| Точность | **побайтовая** — путь не проходит через модель |
| Стоимость промта | ~320 токенов, только если ссылки есть |

Промт CAS измерим: `cas_token_cost()` возвращает его стоимость, чтобы она была
видна в замере, а не растворялась в «прочем».

## 8. Статус реализации

| Часть | Состояние |
|---|---|
| Интерфейс (`memory/cas.py`) | **реализован**: хеш, нормализация, замена, SQLite |
| Связка с ядром (`memory/linking.py`) | **реализована**: `link_cas(chunk, cas)` |
| Тесты | **зелёные**: детерминизм хеша, round-trip, коллизии, связка |
| Прямой доступ к CAS (`resolve_many`) | **реализован**, Архивариус в этом пути не участвует |
| Промт доступа к CAS | **реализован** (`memory/cas_prompt.py`) |

**Связка реализована как явная функция**, а не как побочный эффект записи в
память. Причины две:

1. **Понятность состояния.** Если бы замена происходила внутри
   `MediumMemory.append_chunk`, стало бы неясно, в каком виде чанк пришёл —
   до обработки или после. Явный вызов оставляет решение вызывающему.
2. **Разделение ответственности.** Связка меняет `content`, дополняет
   `cas_refs` и пересчитывает `tokens_after`, но **не пишет** чанк в стек.
   Запись — дело памяти, и смешивать эти действия незачем.

`link_cas` возвращает **новый** чанк: исходный не мутируется. Это проверено
тестом — иначе вызывающий не смог бы сравнить состояние до и после.

**Что осталось:** Архивариус. Он агент с LLM (инвариант 7), его разработка
выходит за рамки реорганизации. Для него уже есть точка входа —
`LongMemory.read(n)`, которая только читает и не может изменить чанк.
