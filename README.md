# StrongContextConvolution

**SCC (Strong Context Convolution)** — свёртка контекста агента без потери ядра.

Обычная компакция заменяет историю пересказом, и каждый пересказ теряет детали.
Замерено на живой сессии (83 компакции, 114 ходов):

```
фактов в 1-й сводке:        129
к 41-й сводке:                1  (1 %)
к 83-й сводке:                0  (0 %)
```

SCC делает иначе: свёрнутое **помечается и больше не пересматривается**.
Повторная свёртка касается только свежей части, ядро переносится дословно.

---

## Система

**Два канала.** В харнессе разделены системный контекст (роль, правила) и
юзерконтекст (диалог). Через ядро проходит **только юзерконтекст**; системный
контекст идёт в HEAD напрямую. Разделение — на конвертере журнала, то есть на
входе: если роль попадёт в поток, ядро её сожмёт, и отменить это будет нечем.

**HEAD** — служебный раздел в начале контекста: роль, инструкция Архивариуса,
инструкция CAS. Не сжимается, не обрабатывается CAS, не уходит в архив
(инвариант 8).

**Три уровня памяти:**

| Уровень | Что это | В контексте |
|---|---|---|
| **Короткая** | несжатый диалог | целиком |
| **Средняя** | стак сжатых чанков | стак |
| **Долгая** | архив чанков | только инструкция; содержимое — через Архивариуса |

Контекст: `[HEAD] + [средняя] + [короткая]`. При выносе в архив он
**уменьшается**, хотя диалог растёт. Перехода «долгая → средняя» нет.

**Точные данные — напрямую, минуя Архивариус.** Ссылка `CAS?{8-64 hex}?`
разрешается вызовом функции. Архивариус — агент с LLM, а генерация
пересказывает: путь стал бы «похожим». Точные данные обязаны возвращаться
дословно.

**Ядро — три прохода.** I: свёртка смысла. II: точные данные по событиям.
III: мерж. Модель не может одновременно сжимать смысл и копировать значения —
на журнале T2 один проход дал **0 значений из 9 182**.

**Пороги выводятся из рабочей зоны**, не задаются произвольно:

```
T = (Z − HEAD)·r/(r + K + 1) − step      порог сжатия
T_arch = K·c + c/2                        порог архивации
```

При фиксированном пороге память вырождается: проверено симуляцией
([`simulate_memory.py`](_engine/tools/simulate_memory.py)) — режим A душит
короткую память, B переполняет зону, устойчив только C.

## Структура

```
METHODOLOGY.md          указатель: порядок чтения, инварианты, версии
METHODOLOGY_CORE.md     ядро: свёртка сырого контекста
METHODOLOGY_MEMORY.md   три уровня памяти, переходы, инварианты 1–8
METHODOLOGY_CAS.md      CAS: хранилище точных данных
METHODOLOGY_HEAD.md     HEAD: два канала, роль и инструкции
METHODOLOGY_STATE.md    состояния методологии: В_РАБОТЕ / ПРИНЯТ

_engine/core/           ЯДРО (ядро обработки контекста)
  scc_events.py         журнал → поток; --exclude-system, --system-out
  scc_run.py            этапы I/II/III (LLM)
  scc_chunk.py          изъятие ядра, сшивка, гейт (без LLM)
  prompts/              промты трёх этапов
  schemas/              контракт чанка

_engine/memory/         ПАМЯТЬ
  short.py medium.py long.py   три уровня
  stack.py              порядок по числовому n, chain.json
  cas.py cas_prompt.py  хранилище точных данных и его инструкция
  head.py               сборка HEAD
  config.py             пороги: вывод из рабочей зоны
  linking.py schema.py tokens.py

_engine/tools/          утилиты
  check_state.py        контроль состояний методологии
  measure_memory.py     замер токенов по уровням
  simulate_memory.py    устойчивость порогов
  experiment_role_rules.py   какие инструкции роли меняют поведение
  experiment_role_decay.py   выветривается ли роль в длинной сессии

_test/                  тесты (292 в 11 наборах: run_all.py)
_docs/                  architecture.md, measurements.md
_research/              отчёты R-SCC-01..06, замеры, дефекты
_rollout/               внедрение в харнесс
runtime/                рабочие данные диалогов — НЕ в git
```

## Запуск

```bash
python3 _test/run_all.py                              # все тесты, сводка
python3 _engine/tools/check_state.py --gate           # 0 = можно реализовывать
python3 _engine/tools/measure_memory.py --window 262144 --steps 3000
python3 _engine/tools/simulate_memory.py              # устойчивость порогов
```

Тесты модель **не вызывают**: всё, что требует сети, вынесено в `_research/`.

## Результаты

| Проверка | Результат |
|---|---|
| Тесты | **292** в одиннадцати наборах |
| Пригодность ядра (14 вопросов) | **14/14** — не хуже сырого потока (13/14) |
| Стоимость прогона свёртки | **×3,1 дешевле** (129 938 против 401 734 prompt-токенов) |
| Сжатие | ×131 на однородном материале, ×13,7 на живой сессии |
| Покрытие событий | 159/159 и 891/892 |
| Сохранность ядра при сшивке | 140/140 имён файлов, потерь 0 |
| Оборот памяти без LLM | проверено разбором исходников через AST |
| Понимание ссылок CAS агентом | 4 сценария из 4, с первой попытки |
| Контекст ограничен | потолок **73 % окна**, экономия растёт с длиной сессии (×3,6 → ×21,5) |
| Влияние роли на поведение | **есть, но выветривается**: расходящееся правило 0,02 → 0,74, к концу диалога 0,30 |

**Чего SCC не делает.** Не сохраняет несжимаемые значения: хеши и дампы —
9 182 на входе → **0** на выходе. Это фильтр по силе смысла, а не дефект: у имени
файла есть структура, у хеша только энтропия. Модель не выдумывает отсеянное,
а ставит указатель.

## Состояния методологии

| Состояние | Разрешено | Запрещено |
|---|---|---|
| **В_РАБОТЕ** | редактировать методологию | любые работы по реализации |
| **ПРИНЯТ** | реализовывать | править без обращения к пользователю |

Если **хотя бы одна** методология в `В_РАБОТЕ`, реализация запрещена
**полностью**. Меняет состояние **только пользователь**. Отсутствие состояния —
не разрешение, а неизвестность (код 2).
